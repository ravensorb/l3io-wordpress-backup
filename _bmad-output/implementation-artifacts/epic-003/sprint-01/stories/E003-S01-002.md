# E003-S01-002: Refuse to overwrite a non-empty target


**Implements:** FR-7


As an operator,
I want the tool to stop rather than guess when the target already has content,
So that a mistyped path does not delete a live site.

**Acceptance Criteria:**

**Given** a Site Root that is not empty, or an existing database
**When** a restore is attempted without explicit authorization for that specific destruction
**Then** the run exits non-zero, changes nothing, and names the flag that would authorize it
**And** authorization is specific — a flag permitting file replacement does not thereby permit dropping the database
**And** the flag combination maps through one total function with no default branch (AD-25)
**And** `--cleanfirst` without `--force` against a non-empty target refuses

## Business acceptance criteria

### Outcome

A restore whose target already has content — a non-empty Site Root, or an existing database holding tables — and that lacks the authorization for that specific destruction exits `REFUSED` (3) before anything changes. The message names the target it found (path, or `host:port/db_name` and table count) and the exact flag that would authorize it. Authorizing file replacement never authorizes database replacement, and the reverse. `--cleanfirst` without `--force` against a non-empty target refuses: the destruction is authorized but the target guard is not. A reviewer can tell it happened by running each reachable flag combination against an empty target and a non-empty one, and seeing either the documented refusal or the documented mode — never a guess.

### Non-goals

- Writing the flag→`(RestoreMode, OverrideSet)` table. It lives in `domain/flag_map.py`, Epic 2's; E002-S02-006 registers the restore flags and lands their entries in the same change. This story *consumes* the table and adds the behavioural tests that prove what each entry does to a real target.
- Any new CLI flag. AD-22 permits new flags, but none is needed: the frozen `--mode`, `--cleanfirst` and `--force` carry the authorizations.
- An interactive "are you sure?" prompt — refusing is the outcome (§7.1); automation must not hang.
- The Safety Snapshot that follows an authorized destruction (story 3.3).
- Deciding what "empty" means for a database by logging in as the WordPress user — existence comes from the administrator (AD-29, story 3.4).

## Technical acceptance criteria

### Interface contracts

Files this story changes: `core/restore.py` (Epic 3's; adds the guard); the restore composition root's target-survey step (see story 3.1's OPEN on `cli/restore.py`). Conventions as recorded in story 3.1 — module docstring naming the AD, `from __future__ import annotations`, `__all__`, `core/` pure under `tools/check_purity.py` and the import-linter contracts.

- **The table is consumed, not reimplemented (AD-25).** The composition root calls E002's `domain/flag_map.py` lookup once, keyed on the parser's `(dest, value)` pairs (`FlagCombination`), obtaining `(RestoreMode, OverrideSet)`. `OverrideSet` is a distinct type from `RestoreMode` (E002), so `--force` can only add an override, never select a Mode. This story adds no mapping code, no `if args.force`, and no second lookup anywhere — a contract test greps `src/l3io/wp/backup/` for `args.force`, `args.cleanfirst` and `.cleanfirst` outside `domain/flag_map.py` and `cli/parser.py` and fails on any hit.
- **The guard is pure and lives in `core/restore.py`.** `check_target(mode: RestoreMode, overrides: OverrideSet, target: TargetState) -> None`, called by `build_restore_plan` (story 3.1) before any phase is planned; `mode` has no default (AD-5, `tools/check_mode_defaults.py`). It raises `NonEmptyTargetError(RefusedError)` with structured fields `part: Literal["files", "database"]`, `found: str` (the canonical Site Root, or `host:port/db_name`), `detail: str` (entry count or table count), `authorizing_flag: str`. `authorizing_flag` is looked up from the same E002 table — the flag combination whose entry yields an `OverrideSet` waiving this `part` for this mode — never typed into the message.
- **Specificity.** The waiver for `files` and the waiver for `database` are separate `OverrideSet` members; `check_target` checks each part the mode touches against its own member. A mode touching both parts with only one waiver refuses for the other part, naming it.
- **`TargetState` inputs, from query ports only.** `site_root_empty`: the Site Root contains no entry other than those the Archive's own `wp-config.php` placement rule excludes — exactly "no directory entries" unless E002's descriptor says otherwise; computed by `SiteFilesQuery.is_empty(site_root)`. `database`: E003-S02-004's `DatabaseTargetState`, from database's `survey` with administrator credentials (`database_exists`, `table_count`). A database that exists with `table_count == 0` is empty for this guard; one that does not exist is empty.
- **Mapping to exit codes.** `NonEmptyTargetError` is a `RefusedError`, so E002-S02-006's `cli/exit.py::exit_code_for` maps it to `ExitCode.REFUSED` with no new arm — E002-S02-006's docstring already records "FR-7 … refusals → `REFUSED`". This story adds no `ExitCode` member.
- OPEN: **the table's contents are E002's.** Which combination reaches each Mode and which `OverrideSet` `--force` yields per part are decided in E002-S02-006's `domain/flag_map.py` (itself an OPEN there). In particular FR-6 requires `all-clean` to need both destructions authorized separately, and §7.1 forbids `--force` authorizing all destruction at once; with only `--cleanfirst` and `--force` on the frozen surface, whether `--force` waives both parts' target guards (a waiver, not a destruction authorization, so AD-25-compliant) or must be per-part is the table's decision. This story's tests read the table and assert behaviour against it; they do not fix it.
- OPEN: **depends on story 3.1's OPENs** — the restore composition root (`cli/restore.py`) and the `SiteFilesQuery` port (`ports/*`, Epic 2's).

### Error and edge case handling

- `--cleanfirst` without `--force`, non-empty Site Root: `REFUSED`, naming `--force` (AD-25's worked case); the recording command log is empty.
- Non-empty Site Root, no flags, mode `all`: `REFUSED` for `files`, naming the authorizing flag; the database is not contacted beyond the `survey` query.
- Both parts non-empty, only one authorized: `REFUSED` naming the unauthorized part. When both are unauthorized, both are named in one refusal (one exit, one message, two `part` entries), so the operator does not discover them one Run at a time.
- Empty Site Root and absent database: no refusal, no override needed.
- Site Root does not exist: E002's `resolve(strict=True)` fails first → `InvalidSiteDescriptorError`; never treated as "empty".
- Site Root is a symlink to a non-empty directory: canonicalised by E002 before the check, so the target's real content is checked.
- Site Root unreadable (permission denied while listing): refuse (`REFUSED`, `detail` naming the error) — an unknown state is never "empty" (NFR-1).
- Database survey cannot run (no admin credentials, unreachable): the error from story 3.4 (`CREDENTIALS` / `UNREACHABLE`), never "empty".
- Dry Run: the guard runs for real (it consumes only query results), so `--whatIf` refuses with the same code and message.
- A flag combination with no table entry is unreachable at runtime because E002's `tests/contracts/test_flag_map.py` derives its scope from the parser; this story adds no fallback for it.

### Observability requirements

- Refusal logged once as ERROR `restore_refused` with `reason: "non_empty_target"`, `parts` (list), `found`, `detail`, `authorizing_flag`, `restore_mode`; the same facts in the stderr message.
- On proceeding, `target_checked` (INFO) with `site_root_empty`, `database_exists`, `table_count` and the overrides that were applied, so a log reader can see that a destruction was authorized and by which flag.
- Carries `run_id` through `merge_contextvars` (E002-S02-005).

### Security considerations

- The refusal names paths and the database `host:port/name` only — never a username or password; covered by E002-S02-004's `credential_sentinel` applied to the refusal path.
- The guard runs before the Safety Snapshot and before any command adapter, so a mistyped `--wp-dir` pointing at a live site is refused without that site being read beyond a directory listing and an administrator `survey`.
- Site Root listing does not follow symlinks out of the Site Root and does not read file contents.

### Testability approach

- `tests/unit/core/test_target_guard.py` (pure): parametrised over **every key of E002's `FLAG_MAP`** — scope from the table, which is itself derived from the parser — crossed with `TargetState` ∈ {empty/empty, files non-empty, database non-empty, both}; asserts refuse-or-proceed and, on refusal, `part` and `authorizing_flag`. A dedicated case asserts `--cleanfirst` without `--force` on a non-empty Site Root refuses naming `--force`.
- Specificity test: for each mode touching both parts, an `OverrideSet` waiving only `files` refuses for `database` and vice versa.
- `tests/contracts/test_no_flag_reads.py`: the `args.force` / `args.cleanfirst` grep above, scope the walked `src/l3io/wp/backup/` tree (asserted non-empty), plus a planted-violation case in a temp tree proving it fires.
- `tests/integration/test_restore_refusal.py` (`@pytest.mark.integration`): non-empty fixture Site Root and populated database; each refusing combination exits `REFUSED`; Site Root tree and `CHECKSUM TABLE` unchanged; no snapshot written; stderr names the flag.
- Recording-adapter test: a refused Run makes zero command-port calls.

### Existing-library check

- Flag parsing: stdlib `argparse` via E002's parser; the mapping is E002's table — nothing here parses flags.
- Directory emptiness: `os.scandir` behind the adapter (one `next()` on the iterator), no library needed.
- Database emptiness: `l3io-wp-database` v0.1.0 `survey` (`database_exists`, `table_count`), ADR-0015; database's own `load` additionally refuses a non-empty target without `replace=` (`DATABASE_NOT_EMPTY`), which stays as a second line of defence, not the guard.
