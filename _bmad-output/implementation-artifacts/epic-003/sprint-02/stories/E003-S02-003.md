# E003-S02-003: Take a safety snapshot before destroying anything


**Implements:** FR-8


As an operator,
I want the tool to capture what is there before it overwrites it,
So that a bad restore is reversible.

**Acceptance Criteria:**

**Given** a destructive restore against an existing Site
**When** the run begins
**Then** a Safety Snapshot Archive is written before the first destructive operation
**And** it is verified after writing, and encrypted when encryption is configured — to the configured `age` recipients now, or under the AD-26 passphrase once `l3io-wp-database` 0.2.0 ships (ADR-0014)
**And** its scope is derived from the Restore Mode, covering everything that mode may destroy
**And** it is written outside the Site Root and outside any web-served directory, and its path is reported
**And** if it cannot be written and verified, the destructive restore does not proceed
**And** opting out is explicit and recorded in the run's logs

## Business acceptance criteria

### Outcome

Before the first destructive phase of a restore against a Site with content, the Run writes a Safety Snapshot. It is a full v1 Archive of everything the Restore Mode may destroy, verified after writing (`integrity: VERIFIED`), encrypted when encryption is configured, and stored outside the Site Root and outside any web-served directory. Its path is printed on stdout and logged. It survives the Run, whether the restore succeeds or fails. If it cannot be written and verified, the restore stops with nothing destroyed. The snapshot is taken by the backup path itself **inside the restore's Run**: one Run ID, one workspace, one Site Lock, and no deadlock. An operator who opts out does so explicitly, and the log records that. A reviewer can tell it happened by running a destructive restore, then restoring the reported snapshot path and getting back the pre-restore Site.

### Non-goals

- Pruning or retaining old snapshots — Retention Policy is v1.1 (FR-17); snapshots accumulate until the operator removes them.
- Automatic rollback from the snapshot after a failed restore. The snapshot makes the restore reversible; reversing it is an operator action (a restore of the reported path), guided by story 3.5's journal.
- Implementing encryption. The `age` path is Epic 4's (`adapters/crypto`, story 4.3), reached through the backup path; passphrase encryption arrives with `l3io-wp-database` 0.2.0.
- A second Archive writer, verifier or encryption call specific to snapshots — the snapshot *is* a backup.
- Snapshots for `backup` or `verify` Runs; only restore takes one.

## Technical acceptance criteria

### Interface contracts

Files this story changes: `core/restore.py` (Epic 3's: the pure snapshot-scope and location rules) and the restore composition root (story 3.1's OPEN on `cli/restore.py`), which builds the `take_snapshot` callable that story 3.1's executor runs for the `SNAPSHOT` phase. Conventions as recorded in story 3.1.

- **The snapshot JOINS the restore's Run Context; it never opens a second one (AD-16, AG-9, AG-11).** `take_snapshot` calls E002's backup entry point, the one E002-S02-005's joining test calls, passing the restore's `RunContext`. That entry point goes through `join_or_open(ctx, ...)`. Given a context it creates nothing, binds nothing and configures nothing: no new `run_id`, no second `structlog` configuration, no second workspace, no second `finally` over the workspace. The snapshot's records therefore carry the restore's `run_id`. Nothing in this story calls `open_run`.
- **The Site Lock is re-entrant for the holder, so there is no deadlock (E002-S02-008).** The restore's `open_run(site_root=...)` holds the `LockHandle` in `RunContext.site_lock`, keyed on the canonical Site Root. The joined backup entry point targets the **same** canonical Site Root (`SiteDescriptor.site_root`, never re-resolved from a different spelling), so it acquires nothing and releases nothing. `FcntlSiteLock`'s per-process `{canonical_path: (run_id, depth)}` registry is the second line: even a stray `acquire` for the same path by the same `run_id` increments depth instead of blocking on a second `flock` fd. The lock is released once, by the restore's `finally`, after the last phase.
- **Scope from the Restore Mode (AD-12, AD-5).** `core/restore.py::snapshot_scope(mode: RestoreMode, target: TargetState) -> BackupScope | None` maps `files`/`files-clean` → `FILES`, `database`/`database-clean` → `DATABASE`, `all`/`all-clean` → `ALL`, through a `match` over every member ending in `assert_never`. It then drops a part that is empty in `target` (an absent or table-less database, an empty Site Root). It returns `None`, and `RestorePlan` omits `SNAPSHOT`, only when every part the mode touches is empty. `mode` has no default (`tools/check_mode_defaults.py`). `BackupScope` and the backup path's handling of it are E002-S01-002's.
- **Location (AD-12).** `core/restore.py::snapshot_location(site_root: PurePosixPath, config_dir: PurePosixPath, requested: PurePosixPath) -> PurePosixPath` is pure. It raises `UnsafeSnapshotLocationError(RefusedError)` when `requested` is equal to or inside `site_root`, or equal to or inside `config_dir` when that differs from `site_root` (WordPress's one-level-up `wp-config.php` convention, FR-29, puts the config beside a directory that may be served). The default `requested` is `platformdirs.user_state_path("l3io-wp-backup") / "snapshots" / sha256(canonical Site Root)`, the same per-user state root as E002-S02-008's `locks/`, created mode `0700`. The file name is `<UTC yyyymmddThhmmssZ>-<run_id>.tar.gz`, written as a `file:` Storage Target (E002 grammar) through E002's `LocalArchiveStore` (AD-20 temp name, verify, `os.replace`, mode `0600`, existing name refused).
- **What "web-served" covers, stated so nobody assumes more.** The mechanical check refuses the Site Root and the config directory. It cannot know an arbitrary web server's document roots, so a `requested` directory that a server serves from elsewhere is not detected. The default location (per-user state directory) is never a document root by convention. This limit is written in `snapshot_location`'s docstring and in the CLI help for the location option.
- **Verified after writing (AD-12, AD-6).** E002's `LocalArchiveStore.publish()` already verifies the staged file before `os.replace`. After publish, `take_snapshot` additionally runs E002's `adapters/tar.py::verify_archive` on the final path and requires `passed is True` and `integrity is Integrity.VERIFIED`. A `STRUCTURAL_ONLY` snapshot is impossible for a v1 writer and is treated as failure. It returns frozen `SnapshotResult(path: PurePosixPath, scope: BackupScope, encrypted: bool, bytes: int, integrity: Integrity)`.
- **Encryption (AD-12, AD-26, ADR-0014).** When encryption is configured, the joined backup runs with that configuration, so the snapshot's payload members are `age`-encrypted to the configured recipients through `l3io-wp-database` (Epic 4 story 4.3's backup path). A passphrase-only configuration is refused with `EncryptionUnavailableError(RefusedError)` naming `l3io-wp-database` 0.2.0, until that release lands `passphrase=`. **No silent plaintext snapshot:** when no encryption is configured, the Run proceeds and says so explicitly on stderr (`safety snapshot is NOT encrypted: <path>`) and in a WARNING record.
- **Refusal if not written and verified (FR-8).** Any failure in `take_snapshot` (write, publish, verify, encryption unavailable, location unsafe, disk full) propagates as `SnapshotFailedError(RefusedError)` carrying `cause`. Story 3.1's executor stops before `CLEAN`/`EXTRACT`/`LOAD_DUMP`. A failed snapshot's temporary file is discarded by `LocalArchiveStore`, and no partial snapshot is left at the final name.
- **Opt-out is explicit (FR-8, §7.1).** The restore composition root takes a required `snapshot: SnapshotPolicy` (`TAKE` / `SKIP`, a closed `StrEnum`) with **no default** at any function that consumes it. `SKIP` removes `SNAPSHOT` from the plan and logs `safety_snapshot_skipped` at WARNING with `opted_out_by` (the flag or the API argument).
- **Snapshot path survives the Run.** It is outside `RunContext.workspace`, so the workspace `finally` never touches it. Story 3.5's Run Journal is written to the snapshot's directory (AD-18).
- OPEN: **the backup entry point that accepts a `RunContext` is not named by E002.** E002-S02-005 asserts the joining behaviour against "the backup entry point" but names only `cli/backup.py::run_backup(args) -> int`, which takes CLI args. This story needs a callable taking `(site: SiteDescriptor, scope: BackupScope, target: StorageTarget, *, ctx: RunContext)` in E002's `cli/` or `core/backup` composition. Dependency on Epic 2.
- OPEN: **CLI surface for the opt-out and the snapshot location.** Both are new flags (AD-22 permits them; proposed `--no-safety-snapshot` and `--snapshot-dir`) in `cli/parser.py`, Epic 2's. Each is a `store_true`/value action, so E002's `test_flag_map.py` will demand a `FLAG_MAP` dimension for any that affects `(RestoreMode, OverrideSet)`. Neither should, and that needs stating in the table's docstring. Dependency on Epic 2.
- OPEN: **AD-26's default when no encryption is configured** is "a product decision recorded before v1.0 ships, not a builder's choice". This story assumes *proceed, said explicitly*, because refusing would make every restore unusable without key setup. That assumption needs the product decision before release.
- OPEN: **FR-6 requires the Restore Mode recorded in the Safety Snapshot's Manifest.** E002-S01-001's `Manifest` has no such field, and `domain/archive_format.py` (the only place a Manifest key may be defined) is Epic 2's. Proposed: an optional `origin: {"kind": "safety_snapshot", "restore_mode": ..., "run_id": ...}` key, which forward-compatible reads ignore. Until it lands, the mode is recorded in the logs and the journal only.
- OPEN: **encryption depends on Epic 4 (story 4.3), which runs in parallel with Epic 3**, while Epic 3 declares a dependency on Epic 2 only. Until 4.3 lands, a Run with encryption configured refuses with `EncryptionUnavailableError` rather than writing plaintext (NFR-1).

### Error and edge case handling

- Snapshot directory not creatable or not writable: `SnapshotFailedError` → `REFUSED`, naming the path; nothing destroyed.
- Disk fills mid-snapshot: `LocalArchiveStore` discards the temp file; `SnapshotFailedError`; nothing destroyed; no partial file at the final name.
- Post-publish `verify_archive` fails or reports `STRUCTURAL_ONLY`: `SnapshotFailedError`; the bad snapshot is left in place, named in the error, not deleted (it may still hold the only copy), and the restore does not proceed.
- `requested` inside the Site Root (including through a symlink — canonicalised before the check) or inside the config directory: `UnsafeSnapshotLocationError` → `REFUSED`.
- Database part touched but the database is absent, or the Site Root part touched but empty: that part is dropped from the scope, and the snapshot covers the rest. When both are empty, there is no `SNAPSHOT` phase, and `safety_snapshot_not_needed` is logged with the reason.
- `--mode files` against a site whose database is unreachable: the snapshot scope is `FILES`, so no database is contacted (E002-S01-002 behaviour of the `files` scope).
- Encryption configured with a passphrase only, before database 0.2.0: `EncryptionUnavailableError` naming the release; nothing destroyed.
- A second process tries to restore or back up the same Site while the snapshot is being written: refused `LOCKED` by the held, re-entrant lock (the join did not release it).
- An entry point that wrongly calls `open_run` inside the restore: `RunContextActiveError` → `REFUSED` immediately. A nested Run is an error, never a hang.
- Dry Run: the joined backup runs with the Run Context's dry-run adapter set, so no snapshot file is written, the planned action `safety snapshot of <scope> to <path>` is reported, and the location check and encryption-availability check still run for real.
- Restore fails after the snapshot: the snapshot remains, and its path is repeated in the failure message.

### Observability requirements

- `safety_snapshot_written` (INFO) with `path`, `scope`, `bytes`, `encrypted`, `integrity`, `restore_mode`. The same path is printed on stdout as a line a script can grep (`safety snapshot: <path>`).
- `safety_snapshot_not_encrypted` (WARNING) with `path` when no encryption is configured.
- `safety_snapshot_skipped` (WARNING) with `opted_out_by`; `safety_snapshot_not_needed` (INFO) with the empty parts.
- The `SNAPSHOT` phase emits one `phase_completed` (E002-S02-005 `phase()`), and the joined backup's own phase records nest under it with the **same** `run_id`. There is exactly one `run_started` and one `run_finished` for the whole restore.

### Security considerations

- The snapshot contains the entire database and Site Root. It is written mode `0600` in a `0700` directory under the per-user state root, never inside the Site Root or config directory, and is encrypted when configured. When it is not encrypted, the operator is told, never left to discover it.
- The snapshot's Manifest carries no credential and no key material (E002 Manifest rules; ADR-0014).
- The location check canonicalises `requested` with `resolve()` before comparing, so a symlink into the Site Root is refused.
- E002-S02-004's `credential_sentinel` covers the snapshot path, because it runs inside the full restore that story 3.1 instruments.

### Testability approach

- **No-deadlock proof — `tests/integration/test_snapshot_joins_run.py`** (unmarked where it can use a database double, `@pytest.mark.integration` for the database scope). It runs the real CLI in a subprocess with `subprocess.run(..., timeout=120)` and **the real `FcntlSiteLock`** (no recording double): a destructive `all` restore against a non-empty fixture Site, with `--log-format json`. Assertions:
  - the process exits `OK` before the timeout (a deadlock fails as `TimeoutExpired`, not as a hang);
  - the JSON stream has exactly one distinct `run_id`, exactly one `run_started`, one `run_finished` and one `site_lock_acquired`;
  - every `phase_completed` from the joined backup carries that `run_id`;
  - the snapshot path printed on stdout exists, is outside the Site Root, and passes `verify_archive` with `VERIFIED`;
  - after exit, the lock is immediately acquirable.
- **The lock is held across the snapshot — same file.** A hook pauses the Run inside `SNAPSHOT`. A second CLI process against the same Site Root, spelled through a symlink, exits `LOCKED` naming the first Run's `run_id`. The first Run is then released and completes.
- **Nesting is an error, not a hang — `tests/unit/cli/test_snapshot_join.py`.** A variant `take_snapshot` that calls `open_run` instead of joining raises `RunContextActiveError` within the test's default time. A recording `SiteLock` shows zero `acquire` calls from the joined path for the same Site Root.
- `tests/unit/core/test_snapshot_scope.py`: parametrised over `list(RestoreMode)` × `TargetState` variants. Asserts the scope covers every part the mode may destroy (cross-checked against story 3.1's plan: every part with a destructive phase is in the scope), and `None` only when all touched parts are empty.
- `tests/unit/core/test_snapshot_location.py`: inside Site Root, equal to Site Root, inside a one-level-up config directory, a symlink into the Site Root (resolved by the caller) → refused; the per-user default → accepted.
- `tests/unit/adapters/test_restore_runner.py` (story 3.1's): a `take_snapshot` that raises yields an empty destructive-command log; `SKIP` yields no `SNAPSHOT` phase and the WARNING record.
- `tests/integration/test_snapshot_reversible.py` (`@pytest.mark.integration`): restore over a populated Site, then restore the reported snapshot with the same mode, and assert the Site Root tree and `CHECKSUM TABLE` equal the pre-restore state.

### Existing-library check

- Writing, publishing and verifying the snapshot: E002's backup path, `LocalArchiveStore` and `verify_archive`. This story writes none of them a second time (the DRY choice AD-16 names).
- Encryption: `l3io-wp-database` v0.1.0 `encryption` (`age` recipients) through Epic 4's backup path; passphrase with database 0.2.0 (ADR-0014). No `pyrage`, no cipher here.
- Per-user state directory: `platformdirs.user_state_path`, the dependency E002-S02-008 adds.
- Hashing the Site Root for the directory name: stdlib `hashlib`. Timeouts in the no-deadlock test: stdlib `subprocess.run(timeout=)`, so no `pytest-timeout` dependency is added.
