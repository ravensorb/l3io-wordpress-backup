# E003-S02-004: Report honestly what the database restore did


**Implements:** FR-9


As an operator,
I want to know whether the database was actually restored,
So that I am not told "done" when nothing happened.

**Acceptance Criteria:**

**Given** a restore covering the database
**When** it completes
**Then** it either restored, or exited non-zero stating why
**And** encountering an existing database is never silently treated as success
**And** it reports which of the database and user it created, from `l3io-wp-database`'s `EnsureResult` (`created_database`, `created_user`, `password_set`, `granted`)
**And** existence is read from database's `survey` with administrator credentials — a failed login by the account being provisioned is evidence about the account, never about the database (AD-29)
**And** provisioning is database's `ensure`; this package issues no `CREATE DATABASE`, `GRANT` or `DROP DATABASE` itself, so AD-28's escaping is database's (ADR-0015)

## Business acceptance criteria

### Outcome

A restore whose Restore Mode includes the database ends in exactly one of two ways:

- **Exit `OK`, with a report** naming the database the site now runs on, whether this Run created that database, created the WordPress user, set its password and granted it access (from `l3io-wp-database`'s `EnsureResult`), and how many bytes the load moved.
- **Exit non-zero, with a stated reason.**

"Done" is never printed for a database that was not loaded. An existing database is never mistaken for a restored one. Whether the database and user already existed is decided by the administrator's view of the server, never by whether the WordPress account could log in. A reviewer can tell it happened by restoring onto three servers — fresh (no database, no user), user-only, and fully populated — and reading three different, accurate reports.

### Non-goals

- The staging database, the cutover, and removing the database that loses it — story 3.5. This story reports on what 3.5's sequence did.
- The FR-7 refusal over an existing database (story 3.2). This story supplies the administrator-read `DatabaseTargetState` that 3.2's guard consumes.
- Administrator credentials from AWS Secrets Manager or the environment — Epic 5 (story 5.1). This story uses the frozen `--admin-username` / `--admin-password` and the library's explicit argument.
- Relocated database name, host or user (`--new-db-*`) — Epic 7.
- Issuing any SQL. Escaping a grant pattern (AD-28) is database's; this package proves the outcome, not the escaping.

## Technical acceptance criteria

### Interface contracts

Files this story changes:

- `core/restore.py` (Epic 3's): the report value and its pure derivation.
- `adapters/staging.py` (Epic 3's): it records `EnsureResult` and the load's `TransferResult` as domain values.
- The restore composition root: administrator credential resolution, and printing the report.

Database calls are made only through `adapters/database.py` (Epic 2's, ADR-0015). Conventions are as recorded in story 3.1.

- **Existence from the administrator only (AD-29).** `DatabaseQuery.survey_target(site: SiteDescriptor, admin: CredentialSource) -> DatabaseTargetState` wraps `l3io.wp.database.survey(connection, admin, *, wordpress_user=<site's DB user>, user_host="%", table_prefix=site.table_prefix)` (verified at v0.1.0, `inspection.py` L101). The frozen domain value is `DatabaseTargetState(database_exists: bool, table_count: int, is_wordpress: bool, user_exists: bool | None)`, copied field by field so that no `l3io.wp.database` type crosses into `core/` (AD-14, AD-1). Its docstring states that these facts are observed by the administrator. The WordPress account's own login failure (`1045`) cannot distinguish "database absent" from "account absent", so no field is ever derived from one. Nothing in this package probes existence by connecting as the WordPress user. A contract test enforces this (Testability).
- **Administrator credentials are explicit, never a fallback (AD-9, AD-29).** For any mode that touches the database, the composition root builds the administrator `CredentialSource` from `--admin-username`/`--admin-password` (frozen flags, AD-22) or the library's `admin=` argument, as `l3io.wp.database.Explicit`. If they are absent, the result is `AdminCredentialsRequiredError(CredentialsError)` → `ExitCode.CREDENTIALS`, naming both flags. The WordPress credentials are never substituted, and this is raised before any phase after `VERIFY`.
- **Provisioning is database's `ensure`; this package issues no `CREATE DATABASE`, `GRANT`, `CREATE USER` or `DROP DATABASE` (ADR-0015, AD-28).** `DatabaseCommand.ensure_database(connection, admin, wordpress) -> EnsureOutcome` wraps `ensure(connection, admin, wordpress, *, user_host="%")` (verified at v0.1.0, `provision.py` L308). It maps `EnsureResult.created_database/created_user/password_set/granted` and the verdict's warning codes into the frozen domain value `EnsureOutcome(created_database: bool, created_user: bool, password_set: bool, granted: bool, warnings: tuple[str, ...])`. In the staging design (story 3.5), `connection.database` is the staging name. A `PASSWORD_UNVERIFIED` warning (a `user_host` not matching this machine) is carried into `warnings` and printed.
- **`core/restore.py::DatabaseRestoreReport`** (frozen): `live_database_before: str`, `live_database_after: str`, `ensure: EnsureOutcome`, `loaded_bytes: int`, `load_duration_ms: float`, `previous_database: Literal["dropped", "retained", "absent"]`, `restored: bool`. The `restored` field is `True` only when `load` returned, story 3.5's post-load check passed, and the cutover write completed. It is computed by a pure function from those three facts, so the report cannot say `restored` for a load that did not happen. `RestoreOutcome` (story 3.1) carries `database: DatabaseRestoreReport | None`. This field is `None` exactly when the mode does not touch the database, and a test asserts that equivalence for every mode.
- **Exit discipline.** The restore returns `ExitCode.OK` only if every phase in the plan completed. It also requires `outcome.database.restored is True` whenever the plan contains `LOAD_DUMP`. Any database phase that did not run to completion raises, and is never returned as a value (E002-S02-006's "`run_*` functions either return `OK` or raise"). Each failure maps through `cli/exit.py::exit_code_for` with no new `ExitCode`:

  | Failure | Exit code |
  |---|---|
  | `RefusedError` from database (wrapped) | `REFUSED` |
  | `DatabaseUnreachableError` | `UNREACHABLE` |
  | `AuthenticationFailedError` for the administrator | `CREDENTIALS` |
  | `ProvisioningError` / `TransferError` | `FAILED` |
- OPEN: **`survey_target`, `ensure_database`, and the no-op `NoopDatabase.ensure_database`, are additions to `ports/database.py`, `adapters/database.py` and `adapters/noop.py`, all Epic 2's.** E002-S02-004 names `survey`/`ensure` as "Epic 3 story 3.4", but the Epic List makes `adapters/database` the only legal call site and gives it to Epic 2. This is a dependency on Epic 2, and the same conflict as story 3.1's restore-port OPEN.
- OPEN: **new error classes** (`AdminCredentialsRequiredError`, and the wrappers for database's `RefusedError`/`ProvisioningError`) go in `domain/errors.py`, Epic 2's. E002-S01-001 says "later stories add subclasses here". The ownership table forbids another epic's edit, so this is a dependency on Epic 2 unless that sentence is read as a grant.

### Error and edge case handling

- **Database mode, Archive has no Dump:** `ArchiveHasNoDumpError` → `REFUSED` (story 3.1), stating that the Archive's scope was `files`. This is never a silent skip.
- **Existing live database encountered:** it is reported in the plan (`database_exists`, `table_count`), guarded by story 3.2, and loaded around by story 3.5. It is never interpreted as "already restored".
- **`ensure` refuses** (missing administrator privilege, `USER_ABSENT`-class blockers): `REFUSED`, naming database's finding codes and messages (credential-free, per database's own redaction). Nothing has been created.
- **`ensure` fails part-way:** `ProvisioningError.completed` lists the steps that ran. The report names them (for example "created database; create user failed"), the Run exits `FAILED`, and story 3.5's journal records what to undo.
- **`ensure` succeeds, but database's own post-check finds the account still cannot use the database:** database raises `ProvisioningError`, so the Run exits `FAILED`. This is never reported as granted.
- **Load raises:** the cause is `TransferError` (mid-stream damage, client exit), `RefusedError` (`DATABASE_NOT_EMPTY`, `CROSS_FAMILY_DUMP`, `INCOMPATIBLE_DUMP_SOURCE`, `IDENTITY_REQUIRED`) or `DatabaseUnreachableError`. The Run exits non-zero naming the cause, and `restored` is never set.
- **Administrator authentication fails:** `CREDENTIALS`, naming the administrator account label (never the password). The WordPress account is not tried in its place.
- **Fresh server (no database, no user):** `survey` returns `database_exists=False`, `user_exists=False`. `ensure` creates both, and the report says so. This is the AD-29 case an integration test covers.
- **Account exists, database does not:** the report says the database was created and the user was not (AD-29's reachable case, asserted).
- **Dry Run:** `survey_target`, `check_ensure` and `check_load` run for real, so a missing privilege or an absent account refuses exactly as the real Run would. `NoopDatabase.ensure_database` returns an all-`False` `EnsureOutcome`, and the printed report says "would ensure" rather than "created".

### Observability requirements

- **`database_surveyed` (INFO):** `database`, `database_exists`, `table_count`, `is_wordpress`, `user_exists`, `observed_by: "administrator"`.
- **`database_ensured` (INFO):** the four `EnsureResult` flags, `database` (the staging name) and `warnings`.
- **`database_restore_report` (INFO on success, ERROR on failure):** every `DatabaseRestoreReport` field. The same report is printed on stdout as human lines, or as one JSON object when `--log-format json`.
- database's own `structlog` records (`operation` start/end, verdict warnings) carry the restore's `run_id` through `merge_contextvars` (E002-S02-005).

### Security considerations

- Administrator credentials are resolved by an explicit call, held as database's `Explicit` source, passed only into database functions, and never logged, printed or placed in an exception. E002-S02-004's `credential_sentinel` fixture is extended to seed the administrator password too, across a full database restore.
- No fallback from administrator to WordPress credentials. That fallback would be both a privilege escalation (AD-9) and the reason existence becomes unanswerable (AD-29).
- AD-28 is proven by reachability, not by statement text. After a restore through this package's path, the restored WordPress user can see its own database and **cannot** see a neighbouring `wpX<suffix>`, and connecting with `database=wpX<suffix>` raises.
- This package contains no SQL DDL or DCL. A contract test scans `src/l3io/wp/backup/` for `CREATE DATABASE`, `CREATE USER`, `GRANT `, `DROP DATABASE`, `ALTER USER` and `DROP USER` (case-insensitive, in string literals) and fails on any hit.

### Testability approach

- **`tests/unit/core/test_database_report.py`** (pure): `restored` is derived from (load returned, post-load check passed, cutover written). Every combination except all-true yields `restored=False`. `database is None` exactly for the modes whose plan has no `LOAD_DUMP`, parametrised from `list(RestoreMode)`.
- **`tests/unit/adapters/test_staging_report.py`:** a fake `DatabaseCommand` raising each database error class in turn. The executor raises, the mapped `ExitCode` is the one listed in Interface contracts, and no `database_restore_report` with `restored: true` is emitted.
- **`tests/contracts/test_no_sql_ddl.py`:** the DDL/DCL scan described under Security. Its scope is the walked `src/l3io/wp/backup/` tree, asserted non-empty, plus a planted-violation case proving it fires. This sits beside `tests/contracts/test_no_mysql_client.py`, which stays green.
- **`tests/contracts/test_existence_by_admin.py`:** an AST scan of `adapters/` and `core/`. It fails if any `except` handling an authentication failure (`AuthenticationFailedError`, `1045`) produces a value named or typed as a database-existence fact. This is a heuristic guard, and its docstring says which shapes it does not see. The integration tests below are the real proof.
- **`tests/integration/test_database_restore_report.py`** (`@pytest.mark.integration`, CI MySQL and MariaDB legs):
  - (a) fresh server → report shows database and user created;
  - (b) account exists, database absent → database created, user not (AD-29);
  - (c) populated server with `--force` → existing database encountered and reported, load into staging, `restored: true`;
  - (d) truncated Dump member → non-zero exit, `restored` absent, live database `CHECKSUM TABLE` unchanged;
  - (e) the AD-28 neighbour-reachability assertion.
- Naming and placement follow E002's `tests/unit/<layer>/`, `tests/contracts/` and `tests/integration/` pattern.

### Existing-library check

`l3io-wp-database` v0.1.0 covers everything this story needs: `survey`, `ensure`/`check_ensure` (`EnsureResult`), `load`/`check_load` (`TransferResult`), `Explicit` credentials, and `quote_grant_database` inside `ensure` (ADR-0015, AD-28). No SQL, no driver call and no client-tool invocation is written here. The report is a frozen dataclass. No reporting library is needed, because output goes through E002's `structlog` configuration.
