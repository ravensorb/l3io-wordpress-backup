# E003-S02-005: Survive being killed mid-restore


**Implements:** NFR-1 (AD-18) — the recoverability guarantee FR-9 reports on


As an operator,
I want an interrupted restore to leave my site recoverable,
So that a power cut does not silently produce a half-restored site that still boots.

**Acceptance Criteria:**

**Given** a restore interrupted at any phase
**When** the operator looks at the site
**Then** a durable Run Journal records the phase that was interrupted and what would undo it
**And** a later run refuses to proceed until that journal is resolved, naming the interrupted phase
**And** `wp-config.php` is written to a temporary file and `os.replace`d, so a partial config is never observable
**And** the Dump loads into a staging database through `l3io-wp-database`'s `ensure` and `load(replace=)`, with the live name switched only by that atomic write after the load is checked
**And** the database that loses the cutover is removed with database's `drop_database`, never by SQL issued here
**And** an interrupted load therefore leaves the live site on its original database, untouched

## Business acceptance criteria

### Outcome

A restore killed at any point — SIGKILL, power loss, OOM — leaves the Site recoverable and leaves the next Run unable to pretend otherwise. Specifically:

- **A durable Run Journal names the interrupted phase.** It records the phase that was in progress and what would undo it: the Safety Snapshot path, the staging database name, the previous `DB_NAME`.
- **The next restore against that Site refuses.** It exits `REFUSED` (3), naming the interrupted Run ID and phase, until the operator resolves the journal.
- **An interruption anywhere before the cutover leaves the live site on its original database.** The Dump loads into a staging database, and `wp-config.php`'s `DB_NAME` moves to it only through one atomic, verified write after the load has been checked. The original database is untouched and `wp-config.php` is byte-identical.
- **`wp-config.php` is never observable half-written.**

A reviewer can tell it happened by killing a restore at every journal boundary in turn and observing, each time, a booting site on its original database (or, past the cutover, on the fully-loaded new one), plus a refusal from the next Run naming that phase.

### Non-goals

- **Making the file phases atomic.** `CLEAN` and `EXTRACT` stay individually irreversible. This story journals them and points the operator at the Safety Snapshot (story 3.3) to undo them; it does not stage the Site Root.
- **Automatic recovery or rollback** on the next Run. The next Run refuses and explains; the operator decides.
- **Relocation constants** (`DB_HOST`, `DB_USER`, `DB_PASSWORD`, URLs) — Epic 7. This story writes only `DB_NAME`, for the cutover.
- **Keeping the database name stable across restores.** The site ends up on the staging database's name; renaming a database back is SQL this package does not issue (ADR-0015). The new name is reported, and a consequence of AD-18 as written.
- **Durability against a host whose storage ignores `fsync`.**

## Technical acceptance criteria

### Interface contracts

Files this story adds: `adapters/journal.py` and `adapters/staging.py`, both Epic 3's per the Epic List. It also changes `core/restore.py` (pure journal-entry and undo derivation) and the restore composition root (story 3.1's OPEN). Conventions are as recorded in story 3.1; both adapters implement split ports (`*Query` / `*Command`, E002-S02-007), with no-op command twins.

- **Database `load(replace=)` semantics, read at v0.1.0 (`transfer.py` L759–L808, L865).** `replace` is a **confirmation token**, not a switch:
  - when the target database exists and holds tables, `load` refuses (`DATABASE_NOT_EMPTY`, a blocker) unless `replace == connection.database`;
  - a mismatched value is `CONFIRMATION_MISMATCH`;
  - `load` then streams into `connection.database` itself, with no rename and no swap. Its docstring says "load into a staging database and switch to it only after the load is checked".

  There is therefore no conflict with AD-18's wp-config cutover: database performs no switch; the switch is the `DB_NAME` write below. This package calls `load` with `connection.database` set to the **staging name** and `replace=None`. A freshly-ensured staging database is empty, so no confirmation is needed, and a non-empty staging database (a name collision) is refused by database rather than loaded over. A contract test asserts no call site passes `replace=` equal to the live name, or passes `replace` at all.
- **Staging (`adapters/staging.py`, AD-18.3).**
  - **Staging name:** `core/restore.py::staging_name(live: str, run_id: str) -> str` returns `f"{live[:51]}_l3s_{run_id.replace('-', '')[:8]}"`. It is pure, ≤ 64 characters (database's `MAX_DATABASE_NAME`), and checked with `l3io.wp.database.validate_database_name`.
  - **Creation:** `DatabaseCommand.ensure_database(Connection(host, staging, port), admin, wordpress)` (story 3.4's wrapper over `ensure`). This creates the staging database, and the WordPress user and its escaped grant if absent, and records the `EnsureResult`.
  - **Load:** `DatabaseCommand.load_dump(Connection(host, staging, port), wordpress, source, replace=None, identities=...)` wraps `load`, so the Dump goes in as the WordPress account. `source` is the Dump member streamed from the Archive (AD-21, no `bytes`).
  - **Post-load check:** a query, `survey(Connection(host, staging, port), admin, table_prefix=site.table_prefix)`. It must return `is_wordpress is True` and `schema_version is not None`. Otherwise `StagingCheckFailedError(BackupError)` → `FAILED`. This is structural, and its docstring says so.
- **Cutover — the only place the live name changes (AD-18.2, AD-18.3).** After the post-load check passes, the `DB_NAME` constant in the target's `wp-config.php` is set to the staging name through `l3io-wp-config` v0.1.0's `WpConfigFile(path).set("DB_NAME", staging)`. Verified at v0.1.0, `adapters/config_file.py` L93–L110, that call:
  1. writes `wp-config.php.l3io-tmp` in the same directory;
  2. reads it back and runs `verify_write` (value-span comparison, ADR-0010);
  3. raises `ReadBackError` with the original unchanged on mismatch;
  4. only then `replace`s it onto `wp-config.php`.

  This package writes no config bytes itself (AD-18.2 delegates the write and its verification). `ReadBackError` and `ConfigWriteError` are re-raised as `ConfigCutoverError(BackupError)` → `FAILED`, with the original byte-identical.
- **`wp-config.php` is never extracted over.** `extract_archive` is called with `roles` excluding `MemberRole.CONFIG` (E002-S01-003's `roles=` parameter), so the only writes to `wp-config.php` in a restore are atomic ones.
- **The loser (AD-18.3, story 3.4's `previous_database`).**
  - **Cutover succeeds, mode names database removal** (`database-clean`, `all-clean`): the previous live database is dropped, after cutover only, as follows:
    1. `revoke(Connection(host, live, port), admin, wp_user, user_host="%", confirm=wp_user)` (v0.1.0 `provision.py` L604). This leaves no stale database-level grant row to be inherited by a later database of the same name.
    2. `drop_database(Connection(host, live, port), admin, confirm=live)` (v0.1.0 L718).

    database's `LIVE_WORDPRESS_SITE` finding is a warning, so it is logged, not a blocker.
  - **Cutover succeeds, mode does not name database removal** (`database`, `all`): the previous database is **retained** and reported (FR-6: a mode not naming database removal drops nothing).
  - **Failure before the cutover:** the loser is the staging database. It is created by this Run, so dropping it destroys nothing that existed. It is removed with `drop_database(Connection(host, staging, port), admin, confirm=staging)` in the error path, and the journal records whether that removal ran.

  No SQL is issued here (story 3.4's `test_no_sql_ddl.py`).
- **Run Journal (`adapters/journal.py`, AD-18.1).** It is split into two ports.
  - **`RunJournalQuery.incomplete(site_root: PurePosixPath) -> JournalRecord | None`.**
  - **`RunJournalCommand`:**
    - `begin_run(header: JournalHeader) -> None`, where `JournalHeader` is `run_id`, `started_at`, canonical `site_root`, `restore_mode`, `archive`, `snapshot_path | None`, `live_database_before`, `staging_database | None` and `wp_config_path`;
    - `phase_started(phase: RestorePhase, target: str, undo: str) -> None`;
    - `phase_completed(phase: RestorePhase) -> None`;
    - `finish_run() -> None`.

  Each write behaves as follows:
  1. It serialises the whole record with `json.dumps`.
  2. It writes `current.json.tmp` with `O_CREAT|O_TRUNC`, mode `0600`, then `os.fsync` on the file.
  3. It runs `os.replace` onto `current.json`, then `os.fsync` on the directory fd.

  The record is therefore either the previous or the new version, durable before the phase it announces begins. `finish_run` renames `current.json` to `completed/<run_id>.json` (the audit trail) and fsyncs the directory. Only `current.json` blocks.

  The `undo` text is derived purely in `core/restore.py::undo_for(phase, header) -> str`, a `match` over every `RestorePhase` ending in `assert_never`:

  | Phase | Undo text |
  |---|---|
  | `CLEAN` / `EXTRACT` | "restore files from Safety Snapshot `<path>`" — or "no Safety Snapshot: opted out by `<flag>`" |
  | `LOAD_DUMP` | "live site untouched; drop staging database `<staging>`" |
  | cutover | "set DB_NAME back to `<live>` in `<wp-config path>`" |
  | loser removal | "`<live>` was being dropped; restore the database from Safety Snapshot `<path>`" |
- **Journal location (AD-18.1).** The per-Site state directory `platformdirs.user_state_path("l3io-wp-backup") / "snapshots" / sha256(canonical Site Root)`. This is story 3.3's default snapshot directory, under the same per-user state root as E002-S02-008's `locks/`, and it is never inside the Site Root. It is created mode `0700`.
- **Refusal on an incomplete journal.** The restore composition root calls `RunJournalQuery.incomplete` after acquiring the Site Lock and before `PREFLIGHT`, as a query, so a Dry Run refuses too. A record raises `IncompleteRunError(RefusedError)` → `ExitCode.REFUSED` (E002-S02-006's docstring: "AD-18 refusals → `REFUSED`"; no new code). The error has fields `run_id`, `started_at`, `interrupted_phase` (the last `phase_started` without a matching `phase_completed`, or `None` meaning "after `begin_run`, before any phase"), `undo` and `journal_path`.
- **Resolution is explicit and specific.** Resolution moves `current.json` to `resolved/<run_id>.json` with a `resolved_at` and `resolved_by` field. It is performed by an acknowledgement that must carry the interrupted Run's ID, so a blanket flag in a cron line cannot resolve a journal nobody read.
- OPEN: **the acknowledgement's CLI surface** — a new flag such as `--resolve-interrupted-run <run_id>`, in `cli/parser.py`, Epic 2's. AD-22 permits new flags. Until it lands, the refusal message names `journal_path` and states that moving it aside is the manual resolution. This is a dependency on Epic 2.
- OPEN: **AD-17 vs AD-18 phase order.** AD-17's enum orders `REWRITE_CONFIG` **before** `LOAD_DUMP`, while AD-18.3 requires the live name to switch "only by the atomic config write … after the load has completed and been checked". The Structural Seed diagram draws `LOAD_DUMP` then `REWRITE_CONFIG`, and says the enum governs. A `DB_NAME` write in `REWRITE_CONFIG` would point the site at an empty staging database if killed before `LOAD_DUMP` finished, which is the exact failure AD-18 forbids. This story satisfies AD-18. Proposed: the `DB_NAME` cutover is journaled as its own step at the end of `LOAD_DUMP` (`phase_started(LOAD_DUMP, target="cutover", …)`), and `REWRITE_CONFIG` remains Epic 7's relocation constants (which never include `DB_NAME` under the staging design). That keeps the enum unchanged, but it is a spine reading, not a spine text, and needs the architect's confirmation.
- OPEN: **`adapters/config_writer` is Epic 7's, and Epic 7 depends on Epic 3.** The cutover needs a config write now. This story calls `l3io.wp.config.WpConfigFile` from `adapters/staging.py` (its own module), with no wrapper of its own. Epic 7's `config_writer` should later absorb that call. The Epic List needs a note, or Epic 7 needs to own the call.
- OPEN: **`l3io-wp-config` v0.1.0's atomic write neither preserves the file mode nor fsyncs.** Read at v0.1.0, `config_file.py` contains no `chmod`/`copymode`/`fsync`. A `0640` `wp-config.php` becomes umask-mode (typically `0644`, world-readable credentials, NFR-3) after the cutover, and a power cut immediately after `replace` can lose the new content on filesystems without replace-ordering guarantees. These are fixes in `l3io-wordpress-config`, raised there. Until then this story asserts the mode is unchanged after the cutover (Testability), and that test fails against v0.1.0 by design.
- OPEN: **journal location when `--snapshot-dir` overrides the snapshot directory** (story 3.3). AD-18.1 says "the Safety Snapshot's directory". A journal that follows an operator-chosen directory could not be found by a later Run without the same flag. This story keeps the journal at the per-Site default directory always, and records the snapshot's actual path in the header. That reading needs confirmation.

### Error and edge case handling

- **Killed after `begin_run`, before any phase:** the next Run refuses with `interrupted_phase=None`, and the Site is unchanged.
- **Killed during `CLEAN` or `EXTRACT`:** the files are partially changed and the database is untouched. The next Run refuses naming the phase, with the snapshot path as the undo.
- **Killed during `ensure` or `load` into staging:** the live database and `wp-config.php` are byte-identical, so the site boots on its original data. The next Run refuses with the undo "drop staging database `<name>`". A leftover staging database is never adopted by a later Run, because the next Run's staging name differs (its own `run_id`) and database refuses a non-empty target without `replace`.
- **Killed between the post-load check and the cutover `replace`:** the original `wp-config.php` is intact. At most a `wp-config.php.l3io-tmp` remains beside it; the journal names it, and it is never read by WordPress.
- **Killed after the cutover, before the loser is dropped:** the site runs on the fully-loaded, checked staging database. The journal says the cutover completed and the drop did not. The undo names the old database.
- **The post-load check fails** (not WordPress, no schema version): the staging database is dropped, `wp-config.php` is not touched, and the Run exits `FAILED`. The journal records the phase and is finished as failed — it is moved to `failed/<run_id>.json`, not left blocking. This is an orderly failure with nothing to recover, because the live site was never changed.
- **The cutover's read-back verification fails:** `ConfigCutoverError`, the original is byte-identical, the staging database is dropped, and the Run exits `FAILED`.
- **Dropping the staging database in the error path itself fails:** the journal stays `current.json` (blocking), with the undo "drop staging database `<name>`". The original error is preserved, and the secondary one is logged.
- **Journal write fails** (disk full, permissions): the phase does not begin, nothing more is destroyed, and the Run exits `FAILED`. A phase is never run unjournaled.
- **Journal unreadable or corrupt on the next Run:** refuse, naming `journal_path` and saying the interrupted phase could not be determined. It is never treated as absent (NFR-1).
- **Incomplete journal for a different Site:** irrelevant. The journal directory is keyed by the canonical Site Root hash.
- **Staging name collides with an existing database:** `ensure` treats an existing database as present. `load` with `replace=None` then refuses `DATABASE_NOT_EMPTY` if it holds tables, so the Run exits `REFUSED` without loading over anything. An empty colliding database is loaded into — it held nothing to lose.
- **Dry Run:** the incomplete-journal query and every database `check_*` run for real. `NoopRunJournal` writes nothing, `NoopDatabase` creates and drops nothing, and no config write occurs. The plan reports the staging name and the cutover as actions.

### Observability requirements

- `journal_written` (DEBUG) per record, with `phase`, `event: started|completed`, `journal_path`.
- `staging_database_created` (INFO) with `staging_database`, plus story 3.4's `database_ensured` fields.
- `staging_load_checked` (INFO) with `staging_database`, `is_wordpress`, `schema_version`.
- `database_cutover` (INFO) with `from`, `to`, `wp_config_path`.
- `previous_database_dropped` / `previous_database_retained` (INFO) with the name.
- `staging_database_dropped` (WARNING, error path).
- `incomplete_run_found` (ERROR), carrying the `IncompleteRunError` fields, which are also printed on stderr.
- The cutover is its own `phase_completed`-shaped record (`phase: "LOAD_DUMP"`, `step: "cutover"`), so its duration is visible separately from the load.
- All records carry `run_id` (E002-S02-005).

### Security considerations

- The journal holds no credential: only names, paths, the Run ID, the mode and undo text. It is mode `0600` in a `0700` directory, written with `json.dumps` (never string formatting). The `credential_sentinel` fixture (E002-S02-004) scans journal files after a full restore.
- `wp-config.php` keeps its mode and owner across the cutover. This is asserted, and is the OPEN against `l3io-wp-config` above. No copy of `wp-config.php` is written outside its own directory, and the `.l3io-tmp` sibling is removed by `l3io-wp-config` on failure.
- The old database's grant is revoked before it is dropped, so a database later created with that name does not silently inherit the WordPress user's access (AD-28's concern, by revocation rather than escaping).
- Staging and loser removal go through database's `drop_database(…, confirm=<exact name>)`. A confirmation mismatch is a blocker, so a wrong-name drop is refused by database.

### Testability approach

- **`tests/integration/test_kill_mid_restore.py`** (`@pytest.mark.integration`, CI MySQL and MariaDB).
  - **Harness:**
    1. The restore runs through the library entry point in a `multiprocessing` spawn child.
    2. The child's adapter set wraps the real `RunJournalCommand` in a test adapter that, after each durable write, sends the record's ordinal to the parent over a pipe and blocks.
    3. The parent SIGKILLs the child at ordinal *k*.
  - **Scope:** *k* is parametrised over every journal write a full `all-clean` restore emits. The scope is derived from a first uninterrupted recording run, asserted non-empty and to include the cutover and the loser-drop writes, so a phase added later is covered automatically.
  - **Assertions per *k*:**
    - `wp-config.php`'s `DB_NAME` is the original name, or (only for *k* after the cutover write) the staging name. It is never anything else, and the file always parses through `l3io.wp.config`.
    - The original database's `CHECKSUM TABLE` is unchanged for every *k* before the cutover.
    - The next Run (a new process) exits `REFUSED` naming the interrupted phase and Run ID.
    - After resolution, a further restore succeeds.
- **`tests/unit/adapters/test_run_journal.py`** (real filesystem in `tmp_path`):
  - `incomplete()` finds `current.json` and computes `interrupted_phase` correctly for each prefix of a write sequence;
  - a crash simulated between temp-write and `replace` leaves the previous record readable;
  - a corrupt `current.json` refuses;
  - `finish_run` and resolution move the file;
  - modes are `0600`/`0700`.
- **`tests/unit/core/test_restore_journal.py`** (pure): `undo_for` is total over `list(RestorePhase)`; `staging_name` stays ≤ 64 characters for a 64-character live name and is distinct per `run_id`.
- **`tests/contracts/test_load_replace.py`:** an AST scan over `adapters/` (scope asserted non-empty) for calls to database's `load`. It fails if any passes `replace=` other than `None`. Its docstring records why: `replace` is database's confirmation token and the switch is the config write.
- **`tests/integration/test_cutover_mode.py`:** a `0640` `wp-config.php` keeps mode `0640` across a restore. This test fails against `l3io-wp-config` v0.1.0 and is marked `xfail(strict=True)` citing the OPEN, so it flips red once fixed upstream and the marker is forgotten.
- Placement and naming follow E002's `tests/unit/<layer>/`, `tests/contracts/` and `tests/integration/` pattern.
