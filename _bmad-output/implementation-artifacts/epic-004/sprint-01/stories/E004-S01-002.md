# E004-S01-002: Read an archive written before the rewrite


**Implements:** FR-10


As an operator,
I want my existing `.tar.gz` backups to still restore,
So that the upgrade does not strand everything I already hold.

**Acceptance Criteria:**

**Given** a manifest-less archive containing `database.sql` and `wp-root/`
**When** it is read
**Then** it is detected as v0 and handled by default, with no opt-in flag (AD-23)
**And** its verification reports `STRUCTURAL_ONLY` rather than claiming integrity it cannot compute
**And** format detection happens in one place, by inspection, never inferred from the filename
**And** nothing in the product writes the v0 format

## Business acceptance criteria

### Outcome

An operator holding Archives written by wpbackup2 0.2.21 or earlier — a gzipped tar with members `database.sql` and `wp-root/…` and no Manifest — runs `wpbackup2 verify --archive <file>` on one and gets a pass reported as `integrity: STRUCTURAL_ONLY`, with output saying integrity was not checked because a pre-rewrite Archive carries no checksums. No flag, environment variable or configuration is needed, and renaming the file to anything (`backup.bak`, no extension) changes nothing. That behaviour is pinned by committed fixture Archives in `tests/fixtures/archives/v0/` that CI reads on every run. One of them was produced by the released 0.2.21 tool itself, and the supported format set is derived from those fixtures, never from a hand-kept list. The same fixtures are what Epic 3's restore tests use to prove a v0 Archive restores. A reviewer can tell it happened by running `verify` against each committed v0 fixture and seeing `STRUCTURAL_ONLY` passes, and against each malformed one and seeing a named failure.

### Non-goals

- Writing the v0 classifier, `ArchiveView`, `Integrity`, `ArchiveProbe` or the verifier. All of these are Epic 2's (`domain/archive_format`, `ports/archive`, `adapters/tar`, `core/verify`; E002-S01-003). This story commits the fixtures and the tests that prove that code reads them. A defect those tests find is fixed in Epic 2's module, as a dependency, not by this story editing it.
- Restoring a v0 Archive onto a Site. That is Epic 3 story 3.1, whose AD-17 phase-order test carries a v0 fixture from this story beside the v1 one (AD-23).
- Upgrading or converting v0 Archives to v1. Nothing writes v0, and nothing rewrites one.
- Encrypted v0 Archives. None exist: 0.2.21 had no encryption.
- `config_path` for v0. It is `None` by E002-S01-003's classifier, and Epic 7 story 7.2 consumes that.

## Technical acceptance criteria

### Interface contracts

This story adds test data and tests only; it adds no module under `src/l3io/wp/backup/`. Conventions are inherited from E002-S01-003, which created `tests/fixtures/archives/` and its `v1/` member, and from E002-S01-001's test layout (`tests/unit/` mirrors package layers, `tests/contracts/`, `tests/adapters/`, the `integration` marker).

- **`tests/fixtures/archives/v0/` (new; Epic 4 owns the v0 fixture Archives and their tests, Epic List ownership note).** Committed binary fixtures:
  - `released-0.2.21-all.tar.gz`: produced once by the **released** `wpbackup2==0.2.21` from PyPI, run as `wpbackup2 backup --wp-dir <site> --mode all --archive <file>` against the CI database service and `tests/data/wp-config.php` plus a few-kilobyte Site Root. If 0.2.21 no longer installs from PyPI (its `wpconfigr` and `mysql-connector` dependencies), it is run from the tag `baseline-pre-rewrite` checkout instead, and the provenance file says so. It is committed as-is and never regenerated. Beside it, `released-0.2.21-all.provenance.json` records the command, the tool version, the Python version, the date and the SHA-256 of the file. This is the fidelity anchor: a fixture written by the code that actually wrote the operators' Archives.
  - `synthetic-*.tar.gz`: generated by `tests/fixtures/archives/v0/make_v0_fixtures.py`, which is checked in beside them. The generator mirrors the legacy writer at tag `baseline-pre-rewrite` (`wpbackup2/classes/wp_internal_backup.py` L80–97). It reproduces that writer's member layout: `stream.add(dump, arcname="database.sql")`, then `stream.add(site_root, arcname="wp-root")`, which yields a `wp-root` directory member followed by `wp-root/<path>` members. It is deterministic, so it writes through `tarfile.open(fileobj=gzip.GzipFile(..., mode="wb", mtime=0), mode="w", format=...)` rather than the legacy `"w:gz"` (which stamps the current time into the gzip header), with a `filter` that fixes member mtimes, uid/gid and names. The set covers: `synthetic-all-pax.tar.gz` (PAX, the default on Python 3.8 and later); `synthetic-all-gnu.tar.gz` (`format=tarfile.GNU_FORMAT`, which is what a 0.2.x run on Python 3.7 or earlier wrote); `synthetic-all-symlink.tar.gz` (a symlink inside the Site Root, stored as a link because legacy `add` does not dereference); `synthetic-all-longname.tar.gz` (a member path over 100 bytes); and `synthetic-renamed.bak` (identical bytes to `synthetic-all-pax.tar.gz` under a non-`.tar.gz` name).
  - `malformed/`: synthetic Archives that must **not** pass. `missing-wp-root.tar.gz`; `missing-database-sql.tar.gz`; `stray-manifest-late.tar.gz` (the v0 shape plus a later `manifest.json`); `escape-dotdot.tar.gz` (`wp-root/../escape`); `escape-absolute.tar.gz` (`/etc/x`); `symlink-escape.tar.gz` (`wp-root/link -> ../../outside`); and `truncated.tar.gz` (`synthetic-all-pax` cut mid-member). The generator writes these too. Fixtures in `malformed/` and `unsupported/` are excluded from the supported set by directory, not by a list.
- **The supported set is derived, not declared (AD-6, AG-6).** E002-S01-003's `tests/contracts/test_supported_formats.py` treats every fixture under `tests/fixtures/archives/<version>/` (excluding `malformed/`) as a member of the supported set. It records v0 as *accepted-without-fixture* until fixtures exist. This story removes that allowance, so a classifier that accepts v0 with no committed v0 fixture fails CI again. That test is a v0 fixture test, which the ownership note gives to Epic 4. If the orchestrator rules the file Epic 2's, the one-line removal is a dependency on E002-S01-003.
- **Consumed interfaces (Epic 2's, unchanged):** `TarArchiveProbe.member_index` / `member_digests`, `domain.archive_format.classify(index) -> ArchiveView`, `Integrity.STRUCTURAL_ONLY`, `core.verify.verify(view, digests) -> VerificationResult`, `adapters.tar.verify_archive(path)`, `adapters.tar.extract_archive(...)`, `cli verify --archive`, and `VerificationReason`.

OPEN: AD-23 and the spine define v0 as "members `database.sql` and `wp-root/`", and E002-S01-003 fails a v0 Archive missing either with `MEMBER_MISSING`. However, 0.2.21's `--mode files` wrote an Archive containing **only** `wp-root/…` (`wp_internal_backup.py` L155–159 calls `__backup_files(..., include_database_dump=False)`), and `--mode db` wrote no Archive at all. Operators' files-only v0 Archives are therefore classified unrecognised, which contradicts FR-10's "existing backups still restore". This story commits `v0/unsupported/synthetic-files-only.tar.gz` and asserts the spine's current behaviour, a named rejection that does not read as corruption, rather than inventing a resolution. Accepting it would need a spine amendment to AD-23/AD-6 and a change to Epic 2's classifier, with `dump_present=False`.

### Error and edge case handling

Each case is a committed fixture with an asserted result. The reasons are E002-S01-003's `VerificationReason` members, and no new reason is added.

- Every Archive fixture directly in `v0/`: `passed=True`, `integrity=STRUCTURAL_ONLY`, `format_version=None`, `dump_present=True`, synthesized roles `dump` for `database.sql` and `site-root` for every `wp-root/…` member. Every member's `checksum` is `None`, so nothing claims a checksum was compared.
- The `wp-root` directory member appears in the index as `wp-root` (tarfile strips the trailing slash). The classifier must recognise the v0 shape from that real spelling, and the PAX, GNU and released fixtures prove it does.
- `synthetic-renamed.bak`: classified exactly as its `.tar.gz` twin. This proves detection is by inspection, never by filename (AD-23).
- `missing-wp-root`, `missing-database-sql` and `synthetic-files-only` fail `MEMBER_MISSING`, or `UNRECOGNISED_FORMAT` naming what was found, whichever E002-S01-003's classifier returns, and never `STRUCTURAL_ONLY`. The message names the members found, so an operator sees "not a recognised Archive shape", not "your backup is corrupt".
- `stray-manifest-late`: `UNRECOGNISED_FORMAT`, not silently v0.
- `escape-dotdot`, `escape-absolute` and `symlink-escape`: `UNSAFE_MEMBER_PATH` during verification, before any extraction (AD-11). When `extract_archive` is driven directly against them, it also refuses, with nothing written outside `tmp_path`.
- `truncated`: `TRUNCATED`. No `EOFError` or `tarfile.ReadError` reaches the caller.
- A v0 Archive is never reported as `VERIFIED` in any output, log record or result value.
- CLI: `wpbackup2 verify --archive <v0 fixture>` exits `ExitCode.OK` (0), and its human output names `STRUCTURAL_ONLY` and the reason. Each malformed fixture exits `ExitCode.VERIFICATION_FAILED` (8) through Epic 2's `exit_code_for`, and no new code is added.

### Observability requirements

- A verify Run against a v0 fixture emits E002-S01-003's single `phase="VERIFY"` record with `format_version="v0"`, `integrity="STRUCTURAL_ONLY"`, `passed=true` and the Run's `run_id`. The test captures structlog output and asserts those fields, which proves AD-23's "the Run's logs report which format was read" for v0 specifically.
- Member names from malformed fixtures appear in logs and messages only in escaped form. The `escape-*` fixtures include a member name with a newline and an ANSI escape, and the test asserts neither reaches the rendered record raw.

### Security considerations

- A v0 Archive is untrusted input (AD-11, NFR-5) and has no checksums, so containment is its only protection. The `escape-*` fixtures are therefore committed permanently, and they run on every Python in the CI matrix inside the existing `AD-11 extraction containment` step.
- The fixtures contain no real data. The released fixture's Dump comes from the CI database seeded with the test schema, and its Site Root is synthetic. The `tests/data/wp-config.php` credentials it embeds are the existing public test values. A test asserts the released fixture's `database.sql` contains no string from the operator-secret patterns E002-S02-004's sentinel uses.
- The generator script runs only when a developer invokes it. It is never imported by the test suite or the package, and it writes only under `tests/fixtures/archives/v0/`.

### Testability approach

- `tests/adapters/test_v0_fixtures.py`: parametrised from a **glob** of the Archive files in `tests/fixtures/archives/v0/` (every regular file except `*.py` and `*.provenance.json`; the passing set) and in `v0/malformed/` plus `v0/unsupported/` (the failing set), with a scope assertion that each glob is non-empty. Each fixture is driven through the real `TarArchiveProbe` → `classify` → `core.verify` path, and its result is asserted per the table under Error handling. The expected outcome is keyed by fixture name in a mapping, and a test fails if a fixture on disk has no entry, or an entry has no fixture. Scope comes from the directory, not from the mapping.
- `tests/contracts/test_v0_fixtures_reproducible.py`: runs `make_v0_fixtures.py` into `tmp_path` and asserts every `synthetic-*` and `malformed/*` output is byte-identical to the committed file. A generator change that is not committed, or a hand-edited fixture, fails. For the released fixture, the committed SHA-256 in `*.provenance.json` must match the file.
- `tests/contracts/test_no_v0_writer.py` proves "nothing in the product writes v0". It has two halves. (a) It greps every module under `src/l3io/wp/backup/` (walked, with a scope assertion) for the literals `"database.sql"` and `"wp-root"`, and fails on any hit outside `domain/archive_format.py`. This extends E002-S01-001's member-name grep, which this story does not edit. (b) For every `BackupScope` member, taken from the enum, it builds an Archive with E002's writer from a tiny in-test Site and asserts it classifies as v1 with a `manifest.json` first member.
- `tests/integration/test_verify_cli_v0.py` (unmarked: it uses committed fixtures and needs no database): it runs `wpbackup2 verify --archive` on `released-0.2.21-all.tar.gz` and `synthetic-renamed.bak` and asserts exit 0 and `STRUCTURAL_ONLY` in stdout. On one malformed fixture it asserts exit 8.
- Extraction: `extract_archive` is driven against `synthetic-all-pax.tar.gz` into `tmp_path`, with the synthesized `site-root` role. The resulting tree's file list and contents must equal the generator's input Site. This is the extraction proof Epic 3's restore builds on.
- AD-21: a v0-shaped Archive of at least 10× `RSS_BOUND_BYTES` is **generated in `tmp_path` at test time** (never committed) with the same generator function. `verify_archive` on it stays under the bound, using the existing calibrated RSS harness in `tests/contracts/test_streaming.py`.
- Released-fixture provenance is the one manual step. The PR that adds it carries the command output in the provenance file, and a reviewer checks it once.

### Existing-library check

Stdlib `tarfile` builds the fixtures. Its `GNU_FORMAT`/`PAX_FORMAT` selection reproduces both legacy header formats, and `gzip.GzipFile(mtime=0)` makes the output deterministic. `hashlib` produces the provenance digest, and `pytest` parametrisation runs the table. The released fixture uses the real legacy tool from PyPI rather than a re-implementation of it. No tar, gzip or JSON parsing is hand-written (AD-23), and no dependency is added.
