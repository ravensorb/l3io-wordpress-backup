# E002-S02-004: Supply credentials without exposing them


**Implements:** FR-15


As an operator,
I want database credentials never to appear where another user or a log reader can see them,
So that backing up a site does not leak the site.

**Acceptance Criteria:**

**Given** any backup or restore that touches the database
**When** credentials must reach a MySQL client tool
**Then** they get there only through `l3io-wp-database`'s `dump` and `load`, which pass them through an anonymous-pipe option file (database ADR-0002); this package builds no argument vector and no option file for a client tool, guarded by `tests/contracts/test_no_mysql_client.py` (ADR-0015)
**And** `MYSQL_PWD` is never set by this package
**And** no credential appears in any log record at any level, asserted against captured structured and stdlib records across a full backup and a full restore
**And** every `repr` and any exception raised to a caller is clean — a traceback is log output under another name

## Business acceptance criteria

### Outcome

Across a full backup and a full verify — and, once Epic 3 lands, a full restore — no database credential appears in any log record at any level (including DEBUG), in any span attribute, in any `repr`, in any exception message or traceback raised to a caller, in any argument vector or environment this package builds, or in any Archive Manifest. Credentials reach the MySQL client tools only through `l3io-wp-database`'s `dump` and `load`. This package owns exactly one redaction implementation, which every log record passes through and which Epic 6's tracing processor must reuse. A reviewer can tell it happened by running the backup with a planted sentinel password at DEBUG and searching every captured output for the sentinel: zero hits. ADR-0015 (`docs/adr/0015-credentials-delegated-to-database.md`, not spec-indexed; reached through AD-7's delegation note) is binding.

### Non-goals

- The option-file / anonymous-pipe mechanism and its `0600`-and-removed assertions (AD-7 enforcement item 5) — `l3io-wp-database`'s ADR-0002 and tests, per ADR-0015. Not re-tested here.
- Credential Providers beyond `wp-config.php` (explicit, environment, AWS Secrets Manager) and `CredentialChain` composition — Epic 5 story 5.1.
- Administrator credentials and provisioning (`survey`, `ensure`) — Epic 3 story 3.4.
- The tracing processor and span attribute redaction wiring — Epic 6 story 6.4; this story ships the function that story must call.
- Passphrase handling for encryption (AD-26) — lands with `l3io-wp-database` 0.2.0 via Epic 4; the redaction set below is extensible so that story adds the passphrase without a second implementation.
- The restore half of "a full backup and a full restore": restore does not exist in E002. This story asserts the backup and verify paths; the restore assertion is written as a reusable fixture that Epic 3 story 3.1 must apply to its path (recorded in Testability).

## Technical acceptance criteria

### Interface contracts

- **`adapters/redaction.py` — the one redaction implementation (AD-7, FR-15, FR-30, AG-14).** `REDACTED: Final = "***"` (the same marker database's `ResolvedCredentials.__repr__` uses, so the family shows one marker). `class SecretRegistry` — a per-Run, thread-safe set of secret strings, with `register(value: str) -> None` (ignores empty strings and values shorter than 4 characters, which would redact ordinary words; a too-short secret is logged once as a warning *without* the value), and `redact(text: str) -> str`, which replaces every registered secret (longest first) with `REDACTED`. `redact_event(event_dict) -> event_dict` is a `structlog` processor that walks the event recursively (strings, mappings, sequences, exception text) and applies `redact`; `redact_argv(argv: Sequence[str]) -> list[str]` applies it to a command line. **There is no other redaction code in the package**: a contract test fails if any module other than `adapters/redaction.py` contains the literal `"***"` or defines a function whose name contains `redact`. This lives in `adapters/` (it is not pure — it holds mutable per-Run state) and is importable by `api/` and Epic 6's `adapters/tracing` without a cycle (layers contract).
- **Registration point.** `adapters/database.py` registers every `ResolvedCredentials.password` with the Run's `SecretRegistry` (the username is not treated as a secret, matching database's `repr`) **immediately after** it calls a source's `resolve()`, before passing the credential to `dump`. The registry instance travels in the Run Context (E002-S02-005, AG-11); before that story lands, the backup composition root creates one per Run.
- **Logging pipeline position.** `redact_event` is installed by E002-S02-005's `configure_logging` as the **last processor before the renderer**, for both structlog-native records and stdlib records routed through `ProcessorFormatter` (so `l3io.wp.config`'s and `l3io.wp.database`'s records are covered too). E002-S02-005 owns the chain; this story owns the processor and asserts its placement.
- **Clean `repr` (AD-7 item 3, AG-14).** `SiteDescriptor.__repr__` (E002-S01-001; it holds no credential) and every package type that holds or wraps a credential source or `ResolvedCredentials` — today the adapter set object the composition root binds — define `__repr__` that shows `password='***'` or omits the field, mirroring database's `Explicit.__repr__`. A contract test enumerates every class in the package (walked, not listed) whose annotations mention `ResolvedCredentials`, `CredentialSource` or a field named `password`, and asserts it overrides `__repr__`.
- **Clean exceptions (AD-7 item 4, AD-14).** `BackupError.__str__` passes its message through the Run's `redact` when one is active; adapters re-raising database errors build their own message from structured fields (source label, host, database name) and never interpolate a credential or the original exception's text unredacted. `raise ... from` preserves the chain; the chained database exception's own text is credential-free by database's contract, and the test asserts the whole formatted traceback (`traceback.format_exception`) anyway.
- **No argument vector, no option file, no `MYSQL_PWD` (ADR-0015).** This package constructs no `subprocess` call to a MySQL client and never writes `MYSQL_PWD` into `os.environ` or an `env=` mapping. `tests/contracts/test_no_mysql_client.py` stays as is; this story adds the `MYSQL_PWD` check beside it.
- **In-process driver (AD-7 "covers PyMySQL too").** This package opens no PyMySQL connection of its own (all database access is via `l3io-wp-database`); a contract test asserts no module under `src/l3io/wp/backup/` imports `pymysql`, so the rule is satisfied by absence and stays checked.

### Error and edge case handling

- A secret that is a substring of another secret: longest-first replacement, so the longer one is fully redacted (unit-tested).
- A secret appearing URL-encoded, or split across two log fields: not caught by string redaction — stated as a limit in the module docstring. The guard is upstream: no code path here builds a URL or connection string containing a credential, asserted by the absence of `pymysql` and of any `mysql://`/`mysql+` literal in the package.
- A secret shorter than 4 characters: not registered (it would redact unrelated text); a single WARNING `secret_too_short_to_redact` is emitted with the source label only. Such a credential still never reaches a log, because no code path logs credentials in the first place — redaction is the backstop, not the primary control.
- A credential source that raises while resolving: database's error is re-raised as `CredentialsError` whose message names the source label and the failure class, never the value; the traceback is asserted clean.
- `--log-level DEBUG` (or the lowest level the CLI accepts) is the test level; raising verbosity must never introduce a credential (FR-20's last consequence).
- Logging configured by a library host instead of our CLI: the processor is still applied to our records when the host uses `configure_logging` from E002-S02-005; when the host configures structlog itself, the host's chain does not contain `redact_event`, and the guarantee rests on the primary control (nothing logs a credential). The `api/` docs (Epic 6) must say so; recorded here so it is not lost.

### Observability requirements

- Every place a command line or a connection is described in a log record uses `redact_argv` / `redact`; logged connection descriptions carry `db_host`, `db_port`, `db_name` and `credential_source` (the label), never `username` with `password`.
- The redaction processor emits no record itself (no "redacted N values" noise per event); a single DEBUG `secrets_registered` with a count is emitted per Run.

### Security considerations

- Threat: credential disclosure through `ps`/`/proc` (argv, environ), logs, tracebacks, `repr` in debugger or error reports, span attributes, and the Archive itself. Each has a mechanical assertion in Testability; none rests on review.
- The `SecretRegistry` holds plaintext secrets for the Run's lifetime only; it is never logged, never pickled, has a `__repr__` that shows only a count, and is dropped with the Run Context.
- The Manifest's `source` projection (E002-S01-001) is asserted to contain no registered secret.
- No credential is written to the Run workspace by this package (the Dump file is database's output and contains data, not connection credentials).

### Testability approach

- `tests/unit/adapters/test_redaction.py`: longest-first, nested structures, exception text in an event, short-secret warning without the value.
- `tests/contracts/test_single_redaction.py`: the `"***"` / `redact`-named-function scan over every module (walked, with a scope assertion), so a second implementation fails CI.
- `tests/contracts/test_credential_hygiene.py`, **the AD-7 items 1–4 assertions**, driven by a reusable fixture `credential_sentinel` (in `tests/conftest.py`) that plants a unique sentinel password in a temp `wp-config.php` and captures (a) all structlog events via `structlog.testing.capture_logs` *and* rendered output, (b) all stdlib records via `caplog` at level 1, (c) every `subprocess.Popen` argv and `env` via a monkeypatch spy, (d) `os.environ` before/after, (e) `repr()` of every object the composition root builds, (f) `traceback.format_exception` of any raised error, (g) the produced Archive's Manifest bytes. ### Existing-library check

- Credential transport to client tools: `l3io-wordpress-database` v0.1.0 (`dump`, `load`; its ADR-0002 pipe option file) — ADR-0015; nothing reimplemented.
- Credential-source `repr` redaction for database's own types: already provided (`ResolvedCredentials`, `Explicit`).
- Log capture in tests: `structlog.testing.capture_logs` and pytest's `caplog`.
- Value redaction itself: no maintained library redacts *known runtime values* across structlog event dicts; structlog ships processors for formatting, not secret scrubbing, and pattern-based scrubbers (e.g. regexes for "password=") are the wrong tool because the secret's shape is unknown and the field names are ours. The custom code is one small processor of a few dozen lines, under the ~100-line threshold that would require an ADR; if it grows past that, stop and raise it.
