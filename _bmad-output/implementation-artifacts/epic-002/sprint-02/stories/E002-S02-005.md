# E002-S02-005: Trace a run end to end by one identifier


**Implements:** FR-20


As an operator,
I want every line a run emits to carry the same identifier,
So that I can pull one run out of a week of logs.

**Acceptance Criteria:**

**Given** any run
**When** it emits records
**Then** every record carries the same Run ID, including those emitted around subprocess boundaries
**And** the Run ID is reported at the start and end of the run
**And** logging is configured once at a composition root and never in a library module
**And** `l3io-wp-config`'s (`l3io.wp.config`) stdlib records are pulled into the same structured stream without that package taking a logging dependency (AD-2, AD-10)
**And** a library caller can bind their own correlation ID and see it on these records
**And** each phase emits `phase`, `duration_ms`, `exit_code` and `bytes` as fields, so `jq` over a log file is sufficient

## Business acceptance criteria

### Outcome

Every record a Run emits — this package's, `l3io.wp.database`'s and `l3io.wp.config`'s — carries the same `run_id` (a UUIDv4), so `jq 'select(.run_id=="…")'` over a week of JSON logs returns exactly one Run, start to finish. The Run ID is printed to the operator when the Run starts and when it ends. Output is human-readable on a TTY by default and JSON when selected or when stderr is not a TTY; `--log-level` defaults to INFO, so a cron job's log is useful without flags. Each phase emits `phase`, `duration_ms`, `exit_code` and `bytes`. A library caller can bind their own correlation ID and see it on these records. The Run Context that carries the Run ID is created exactly once per Run and joined, never duplicated, by any nested entry point.

### Non-goals

- OpenTelemetry spans, the `trace_id`/`span_id` processor and the `otel` extra — Epic 6 story 6.4 (`adapters/tracing`). This story leaves a documented slot in the processor chain for it (see Interface contracts) but adds no tracing code.
- The Site Lock inside the Run Context — E002-S02-008 adds the field and its acquisition; this story defines the Run Context with a `site_lock` field typed as the lock port and populated by that story.
- Dry Run adapter binding — E002-S02-007 owns the adapter set selection; this story's Run Context carries whatever adapter set the root binds.
- Exit-code numbers — E002-S02-006. `exit_code` fields here carry whatever the enum yields.
- Cross-package verbosity *implementation* in `l3io-wp-config` or `l3io-wp-database` — those packages are not edited. Consistency is asserted against their published CLIs (see Interface contracts).
- Log message wording — not part of the §8 contract.

## Technical acceptance criteria

### Interface contracts

- **`cli/context.py` (shared by both composition roots; `api/` imports it, which the layers contract permits since `cli : api` is one layer) — the Run Context (AD-16, AG-11).** `@dataclass(frozen=True, slots=True) class RunContext` with `run_id: str` (UUIDv4 via `uuid.uuid4()`, generated here, never derived from time or path), `started_at: datetime` (UTC, tz-aware), `workspace: Path` (AD-12's private workspace — E002-S01-001's `run_workspace` moves under the Run Context here; no other code creates a workspace), `logger: structlog.stdlib.BoundLogger`, `clock: Clock`, `secrets: SecretRegistry` (E002-S02-004), `adapters: AdapterSet`, `site_lock: SiteLock | None` (populated by E002-S02-008). `ports/clock.py` declares `Clock` (`now() -> datetime`, a query port), with `adapters/clock.py::SystemClock`.
- **Exactly once, joinable.** `open_run(*, adapters: AdapterSet, workspace_parent: Path | None = None) -> ContextManager[RunContext]` creates the context, binds `run_id` with `structlog.contextvars.bind_contextvars`, logs `run_started` (with `run_id`, `started_at`, package version), yields, and in its `finally` logs `run_finished` (with `run_id`, `exit_code`, `duration_ms`), unbinds, and removes the workspace. An "active Run" is defined by a module-level `contextvars.ContextVar[RunContext | None]` (triage E-15: the same context that carries the Run ID). `open_run` while one is active raises `RunContextActiveError(BackupError)` naming the active `run_id`. `join_or_open(ctx: RunContext | None, ...)` is what every entry point calls: given a context it **joins** — creates nothing, binds nothing, configures nothing — and otherwise opens one. A test calls the backup entry point from inside an active Run (the Safety Snapshot shape, Epic 3 story 3.3) and asserts one Run ID, one workspace, one `run_started`.
- **`cli/logging.py::configure_logging(level: str, fmt: Literal["console", "json"] | None) -> None` — the only `structlog.configure` / `logging` root configuration in the package (AD-10).** Called by the CLI's `main` once, before `open_run`; the `api/` root (Epic 6) calls the same function only when asked to. Processor chain, in this order: `structlog.contextvars.merge_contextvars` **first**; `structlog.stdlib.add_log_level`; `structlog.stdlib.add_logger_name`; `structlog.processors.TimeStamper(fmt="iso", utc=True)` (UTC with ISO-8601's explicit `Z` designator — Consistency Conventions' "explicit offset"); `structlog.processors.format_exc_info`; *(Epic 6's `trace_id`/`span_id` processor slots here)*; E002-S02-004's `redact_event`; then the renderer — `JSONRenderer()` for `json`, `ConsoleRenderer()` for `console`. Stdlib records (including `l3io.wp.config`'s `logging.getLogger(__name__)` records and anything third-party) are routed through `structlog.stdlib.ProcessorFormatter` with `foreign_pre_chain` equal to the same pre-renderer processors, attached to one root handler on stderr, so one stream carries everything and `l3io.wp.config` takes no `structlog` dependency (AD-2). `l3io.wp.database` uses `structlog.get_logger` and is covered by the same configuration.
- **CLI flags (AD-22, AG-15).** `--log-level` keeps its v0.2.21 spelling and position (top-level) with its **default changed from `CRITICAL` to `INFO`** (triage E-14; a behaviour fix AD-22 permits, named in the release notes). Accepted values are the stdlib level names, case-insensitive; anything else is a usage error. A new top-level `--log-format {console,json}` is added (AD-22 permits new flags); when omitted, `console` if `sys.stderr.isatty()` else `json`. These match `l3io-wp-database` v0.1.0's CLI (`--log-level` default `INFO`, `--log-format {console,json}`), which is the cross-package verbosity consistency FR-20 asks for; `l3io-wp-config` ships no CLI logging surface to compare.
- **Library rule.** No module outside `cli/logging.py` calls `structlog.configure`, `structlog.configure_once`, `logging.basicConfig`, `logging.config.*`, or adds a handler to the root logger; library modules only call `structlog.get_logger(__name__)`.
- **Per-phase fields (AD-24 "what tracing does not replace").** A helper `adapters/phase.py::phase(name: str) -> ContextManager[PhaseRecord]` (or the existing step runner from E002-S01-001, extended) emits on exit one record `phase_completed` with `phase`, `duration_ms` (monotonic clock), `bytes` (set by the step; 0 when not applicable), `exit_code` (0 on success, the mapped code on failure) and `outcome` (`ok`/`failed`). Every `BackupStep` and the verify step run inside it.
- **Caller correlation ID.** A library caller that has called `structlog.contextvars.bind_contextvars(correlation_id=...)` before entering the API sees `correlation_id` on every record, because `merge_contextvars` is first and `open_run` binds only `run_id` (it never clears pre-existing context variables, and its `finally` unbinds only what it bound).
- **Naming (AG-23).** References to the config package are `l3io-wp-config` / `l3io.wp.config` everywhere in code, docstrings and tests; the string `wpconfigr` appears nowhere under `src/l3io/` (contract test).

### Error and edge case handling

- `open_run` inside an active Run: `RunContextActiveError`, never a second Run ID.
- A failure anywhere inside the Run: `run_finished` is still emitted (from `finally`) with the failure's `exit_code`, and the workspace is removed. A `KeyboardInterrupt`/`SystemExit` also reaches the `finally`; signal-driven termination is E002-S02-008's (SIGTERM handler) and must route through the same `finally`.
- `configure_logging` called twice in one process (a test, or a host calling the API twice): idempotent — it replaces the root handler rather than stacking a second, so no record is emitted twice (asserted).
- Records emitted from a thread spawned inside the Run (database's stderr drainer): `contextvars` do not propagate to a raw `threading.Thread`; records from such threads carry `run_id` only if the thread was started with `contextvars.copy_context().run`. This package starts no threads; the test asserts database's records emitted around `dump` carry `run_id`, and if any do not, that is raised against `l3io-wp-database` rather than patched here.
- Invalid `--log-level` or `--log-format`: argparse usage error.
- stderr closed or a broken pipe (`| head`): logging errors do not mask the Run's real exit code; `logging.raiseExceptions` stays at its default and the CLI catches `BrokenPipeError` on exit.

### Security considerations

- `redact_event` sits after every enrichment processor and before the renderer, so nothing added late escapes redaction; a test asserts its index in the configured chain is `len(chain) - 2`.
- Raising verbosity to DEBUG never introduces a credential (FR-20) — exercised by E002-S02-004's `credential_sentinel` fixture at DEBUG through this configuration.
- The Run ID is random (UUIDv4), so it leaks neither time nor path; the workspace path is logged only at DEBUG.

### Testability approach

- `tests/unit/cli/test_run_context.py`: one Run ID per Run; UUIDv4 format; nested `open_run` raises; `join_or_open` with a context creates no workspace and emits no `run_started`; workspace removed on success and on exception.
- `tests/unit/cli/test_logging.py`: `merge_contextvars` is `chain[0]`; timestamps parse with `datetime.fromisoformat` to a tz-aware UTC value; console renderer on a TTY (pseudo-TTY via `pty.openpty`), JSON otherwise; `--log-level` default is `INFO` read **from the parser** (not a constant in the test); idempotent reconfiguration.
- `tests/contracts/test_logging_configured_once.py`: AST scan of every module under `src/l3io/wp/backup/` (walked, scope-asserted) for the forbidden configuration calls, allowing only `cli/logging.py`.
- `tests/contracts/test_no_wpconfigr_name.py`: the AG-23 string scan.
- `tests/integration/test_run_correlation.py` (`@pytest.mark.integration`): a full backup with `--log-format json` captured from stderr; every line parses as JSON; every line has the same `run_id`, including the `l3io.wp.database` and `l3io.wp.config` records (asserted present — at least one record from each logger name — so the check cannot pass over an empty set); first and last records are `run_started`/`run_finished`; each plan step has one `phase_completed` with the four fields; a pre-bound `correlation_id` appears on every line.
- Tests use `structlog.testing.capture_logs` for unit cases and real stderr capture for the integration case, with `structlog.reset_defaults()` in a fixture so configuration does not leak between tests.
