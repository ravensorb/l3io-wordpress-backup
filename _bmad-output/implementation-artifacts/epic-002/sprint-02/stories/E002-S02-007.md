# E002-S02-007: Rehearse any destructive operation


**Implements:** FR-19


As an operator,
I want to see what a backup would do before it does it,
So that I can check the plan against a production site safely.

**Acceptance Criteria:**

**Given** a backup run as a Dry Run
**When** it runs
**Then** credential resolution, preflight and planning all execute for real
**And** the actions it would take are reported in order
**And** the Site and the Storage Target are unchanged afterwards — the `ArchiveStore` command adapter is a no-op
**And** the plan is equal across the real and the no-op adapter sets
**And** no `if dry_run:` conditional exists anywhere outside a composition root — a Dry Run binds real queries and no-op commands (AD-4)

*(The restore half of FR-19 — "what a restore would do" — is Epic 3's, AG-29.)*

## Business acceptance criteria

### Outcome

`wpbackup2 --whatIf backup --wp-dir <Site Root>` (and the library equivalent, `dry_run=True` at the API composition root) resolves credentials, runs preflight, checks the database is dumpable, plans, and reports the ordered list of actions a real backup would take — then exits with the code the real backup would have had at that point, leaving the Site and the Storage Target byte-identical. A Dry Run that would be refused reports the refusal exactly as the real Run would. This works because a Dry Run binds the real query adapters and no-op command adapters; no `dry_run` conditional exists outside a composition root. A reviewer can tell it happened by diffing the Storage Target directory and the database checksum before and after, and by comparing the reported plan with the plan of a real Run against the same site.

## Technical acceptance criteria

### Interface contracts

- **Every port splits into a query half and a command half (AD-4, AG-12).** Convention for `ports/`: each capability is two `typing.Protocol` classes named `<Capability>Query` and `<Capability>Command` (e.g. `ArchiveStoreQuery`/`ArchiveStoreCommand`, `DatabaseQuery`/`DatabaseCommand`, `ArchiveProbe` which is query-only, `Clock` query-only, `SiteLock` command-only). A query never changes the Site, the database or a Storage Target; a command may. `ports/__init__.py`'s docstring already states this; this story makes it a test (below).
- **No-op command adapters.** `adapters/noop.py` provides one no-op implementation per `*Command` Protocol, named per the Consistency Conventions (`NoopArchiveStore`, `NoopDatabase`, …). Each satisfies its Protocol (checked by mypy and by `isinstance` against `@runtime_checkable` Protocols), performs no effect, records the call it received into an `ActionLog`, and returns a value of the declared type that lets the plan continue (e.g. `NoopDatabase.dump_to` returns `DumpResult(bytes=0, duration_ms=0.0)` and writes nothing; `NoopArchiveStore.stage` returns a `StagedArchive` whose stream is `io.BytesIO`-free — an `os.devnull`-backed writer — so AD-21 holds and nothing accumulates in memory).
- **`AdapterSet`** (frozen dataclass in `cli/context.py`, carried by E002-S02-005's Run Context): one field per port half. Two constructors only, both in composition roots: `real_adapters(...)` and `dry_run_adapters(...)`, where the dry-run set reuses the **same** query instances as the real set and substitutes only command halves. `dry_run` / `what_if` appear only in `cli/` and `api/` — the existing CI step "AD-4 no dry-run conditionals" already greps for this and stays as is.
- **Preflight port (AD-13, AG-20; `ports/*` is E002-exclusive).** `ports/preflight.py`: `class ToolRequirement(frozen)`: `name: str`, `minimum_version: tuple[int, ...] | None`, `needed_for: str` (the plan step that needs it); `class ToolStatus(frozen)`: `name`, `present: bool`, `version: tuple[int, ...] | None`, `path: str | None`; `class Preflight(Protocol)`: `check(requirements: Sequence[ToolRequirement]) -> Sequence[ToolStatus]` — a query. `core/backup.py::build_backup_plan` adds `required_tools: tuple[ToolRequirement, ...]` to `BackupPlan`, derived from the plan's steps. The composition root runs preflight for every requirement **before the first command adapter is called**, in both real and Dry Run; a missing or too-old tool raises `PreflightFailedError(tool, needed_for, found)` → `ExitCode.NOT_READY`, nothing changed. For E002, the `DUMP` step's requirement is satisfied by `l3io.wp.database.check_dump(connection, credentials)` (verified at v0.1.0: returns a `Verdict` whose findings include `CLIENT_TOOL_MISSING`, `CLIENT_SERVER_SKEW`, `MISSING_PRIVILEGE`, `UNREACHABLE`), wrapped as a `DatabaseQuery.check_dump` so the binary check stays database's. `adapters/preflight` (Epic 5) later supplies the generic binary checker; until then the root binds a `Preflight` that only consults `DatabaseQuery.check_dump` for the dump step.
- **The plan is data, and is what a Dry Run reports.** `core/backup.py` returns a `BackupPlan` whose `steps` and `required_tools` fully describe the actions; `cli/backup.py` renders it in order (`1. resolve credentials from wp-config:<path>`, `2. preflight: mysqldump (needed for DUMP)`, `3. dump <db_name> from <host>:<port>`, `4. collect <n> files under <Site Root>`, `5. write Archive`, `6. verify`, `7. publish to file:<path>`) on stdout, and logs each as `planned_action`. The real Run executes the same `BackupPlan` value.
- **CLI.** `--whatIf` (dest `what_if`, top-level, as v0.2.21) is wired; `--what-if` is added as an alias of the same action (triage E-7). The restore subcommand's use of it is Epic 3's.

### Error and edge case handling

- A Dry Run against a site whose credentials fail, whose database is unreachable, or whose `check_dump` verdict blocks: exits with the same `ExitCode` the real Run would, after reporting the actions planned up to that point; it does **not** report "would back up".
- A Dry Run whose Storage Target final name already exists: refused exactly as the real Run (that check is an `ArchiveStoreQuery.exists`, a query, so it runs for real).
- A Dry Run with an unsupported Storage Target scheme: refused at parsing, identical to the real Run.
- `--mode files` Dry Run: no credential resolution and no database preflight, matching the real `files` plan (E002-S01-002).
- Workspace: a Dry Run still creates and removes the Run workspace (it is Run machinery, not a Site or Storage Target write); nothing is written into it by no-op commands.
- A port added later without a no-op command implementation: `dry_run_adapters` cannot be constructed (missing field) — caught by mypy and by the coverage test below.

### Observability requirements

- `run_started` carries `dry_run: true|false` (the only place the flag name appears in a record, bound once at the root as a context variable so every record in the Run carries it).
- Each planned action is logged as `planned_action` with `step`, `ordinal` and the step's parameters (redacted per E002-S02-004).
- No-op command adapters emit `phase_completed` with `outcome="skipped_dry_run"` and `bytes=0`, never `outcome="ok"` — a Dry Run log must not claim an effect occurred (triage E-8).

### Security considerations

- A Dry Run resolves real credentials (FR-19 requires it); they are registered with the Run's `SecretRegistry` and redacted exactly as in a real Run. The `planned_action` rendering is covered by E002-S02-004's `credential_sentinel` fixture, run once in Dry Run mode.
- A Dry Run against production must be provably non-destructive: the guarantee is structural (no command adapter can be reached except through the `AdapterSet`), and the tests below assert it rather than relying on review.

### Testability approach

- `tests/contracts/test_port_split.py`: walks every module under `ports/` (scope-asserted non-empty), collects every `Protocol`, and asserts each is named `*Query` or `*Command` (or is on the explicit, docstring-justified query-only/command-only allowance for `ArchiveProbe`, `Clock`, `Preflight`, `SiteLock` — the allowance is checked to name only Protocols that exist). Then asserts every `*Command` Protocol has exactly one implementation in `adapters/noop.py` and every field of `AdapterSet` is filled in `dry_run_adapters` — scope from the Protocols, not a list.
- `tests/unit/core/test_plan_equality.py` — **the AD-4 plan-equality test**: for each `BackupScope` (parametrised from the enum), build the plan via the composition root's planning path with the real query set (backed by fakes for the database) and with the dry-run set, and assert the two `BackupPlan` values are equal and the rendered action lists are equal.
- `tests/integration/test_dry_run_backup.py` (`@pytest.mark.integration`): against the CI database — snapshot the Storage Target directory listing (names, sizes, mtimes), the Site Root tree and a `CHECKSUM TABLE` of every table; run `--whatIf backup`; assert all three unchanged, exit 0, ordered actions on stdout; then a Dry Run with wrong credentials exits `CREDENTIALS` like the real Run.
- `tests/unit/cli/test_preflight_order.py`: a recording `Preflight` and recording command adapters prove preflight completes before the first command call, in both modes; a failing preflight leaves the recording command log empty.
- The existing CI step "AD-4 no dry-run conditionals" is unchanged; this story adds a planted-violation test (`tests/contracts/test_dry_run_gate.py`) that runs the same `grep` over a temp tree containing `core/x.py` with `if dry_run:` and asserts it fails, so the gate is proven to fire.

### Existing-library check

`typing.Protocol` / `runtime_checkable` express the port split; `os.devnull` provides the discard sink. The database readiness check is `l3io-wp-database`'s `check_dump` (verified at v0.1.0), not a reimplementation. Binary presence (for Epic 5's generic preflight) will use stdlib `shutil.which`. No dry-run framework exists or is warranted; the mechanism is adapter selection.
