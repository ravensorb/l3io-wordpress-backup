# E002-S02-008: Prevent two runs colliding on one site


**Implements:** FR-28


As an operator,
I want a second run against the same site to refuse,
So that an overrunning nightly job cannot race a manual restore.

**Acceptance Criteria:**

**Given** a run holding the lock for a Site
**When** a second run targets the same Site
**Then** it exits non-zero naming the holder, and changes nothing
**And** the lock is keyed on the canonical absolute Site Root path
**And** the lock is held **outside** the Site Root, so no restore scope can delete the lock it is holding
**And** it is acquired by the outermost composition root before the first phase and released in a `finally`
**And** a lock whose holding process is gone is reclaimable with a logged warning; a live one is an error
**And** it binds CLI and library callers identically

## Business acceptance criteria

### Outcome

While one Run holds a Site, a second Run against the same Site — from cron, a systemd timer, a shell or a library caller, as the same user — exits `LOCKED` (E002-S02-006) before reading any Site state, changes nothing, and names the holder's Run ID, PID and start time. The lock is released when the holder ends on success, on failure and on SIGTERM/SIGINT; if the holder was killed outright, the next Run reclaims it with a logged warning instead of needing manual cleanup. The holder itself can re-enter (the Safety Snapshot path in Epic 3 calls back into backup under the same Run) without deadlocking. A reviewer can tell it happened by starting a long backup, starting a second one against the same Site Root (spelled differently — a symlink or a trailing `/..`), and seeing the second refuse with the first's Run ID.

### Non-goals

- Mutual exclusion across different OS users, or across hosts sharing a Site Root over NFS — the lock lives in a per-user state directory (AD-19); two users backing up one Site concurrently are not excluded. Stated, not silently assumed.
- Locking on the database or on a Storage Target: the lock is keyed on the Site Root only.
- The Run Journal and its directory (AD-18) — Epic 3 story 3.5, which places it beside this lock in the same state directory.
- Waiting or retrying for the lock (`--wait`): a held lock refuses immediately; schedulers retry on `LOCKED`.
- Windows — unsupported in v1.x (Stack).

## Technical acceptance criteria

### Interface contracts

- **`ports/lock.py` — `SiteLock` (command-only port, on E002-S02-007's allowance).** `acquire(site_root: Path, holder: LockHolder) -> LockHandle`; `LockHandle.release() -> None`, usable as a context manager. Frozen `LockHolder(run_id: str, pid: int, started_at: datetime, hostname: str)` lives in `domain/lock.py` (pure). Refusal raises `SiteLockedError(BackupError)` with structured fields `site_root`, `holder_run_id`, `holder_pid`, `holder_started_at`; it maps to `ExitCode.LOCKED`.
- **Key (AD-19).** The canonical absolute Site Root path: `Path(site_root).resolve(strict=True)` (symlinks and `..` resolved), computed once by the composition root — the same value E002-S01-001 puts in the Site Descriptor. The lock file name is `sha256(str(canonical).encode()).hexdigest() + ".lock"`, with a sibling `<same>.json` holder record carrying the canonical path in clear for diagnosis.
- **Location (AD-19).** Outside the Site Root, in the per-user state directory: `platformdirs.user_state_path("l3io-wp-backup") / "locks"`, created mode `0700`. On Linux this is `$XDG_STATE_HOME/l3io-wp-backup` (default `~/.local/state/…`); on macOS `~/Library/Application Support/…`. A test asserts the resolved lock directory is not inside the canonical Site Root, and the adapter refuses (`SiteLockLocationError`) if a misconfigured `XDG_STATE_HOME` places it there. Overridable for tests by an explicit constructor argument, never by an environment variable read deep in the adapter.
- **Mechanism — `adapters/lock.py::FcntlSiteLock`.** Opens the lock file (`O_CREAT`, `0600`) and takes `fcntl.flock(fd, LOCK_EX | LOCK_NB)`. An OS-held advisory lock is released by the kernel when the holding process dies for **any** reason, including SIGKILL — so a "lock whose holding process is gone" is never a live lock; what remains is a stale holder record, which the acquirer overwrites after logging `stale_lock_reclaimed` (WARNING) with the previous holder's fields. On `BlockingIOError`, the adapter reads the holder record and raises `SiteLockedError` naming it; if the record is missing or unreadable, it still refuses, naming the lock path. PID liveness (`os.kill(pid, 0)`) is used only to word the warning, never to decide ownership — the kernel lock decides.
- **Re-entrancy for the holder (AD-16, AG-9).** The Run Context (E002-S02-005) holds the `LockHandle` in `site_lock`. An entry point that **joins** a Run Context whose `site_lock` already covers the same canonical Site Root acquires nothing and releases nothing. A joined entry point targeting a *different* Site Root acquires that Site's lock, and releases it itself. `FcntlSiteLock` additionally keeps a per-process registry `{canonical_path: (run_id, depth)}` so a second `acquire` for the same path **by the same `run_id`** increments depth instead of self-deadlocking (flock on a second fd in the same process would otherwise conflict), and a second acquire by a *different* `run_id` in the same process refuses — which `RunContextActiveError` already prevents in practice.
- **Acquired by the outermost composition root (AD-16, AD-19).** `open_run` (E002-S02-005) gains `site_root: Path | None`; when given, it acquires the lock **after** creating the Run ID and **before** the first phase — before resolving credentials or reading `wp-config.php` beyond canonicalising the path (FR-28: "before its first read of Site state") — and releases it in the same `finally` that removes the workspace. `verify` takes no Site lock (it has no Site). The CLI and `api/` both go through `open_run`, so CLI and library callers bind identically; nothing in `cli/` alone acquires it.
- **Released on signal (FR-28, AG-16).** The CLI's `main` installs, for the duration of the Run only, a SIGTERM handler that raises `RunTerminated(BackupError)` (mapped to `FAILED`) so the `finally` chain runs; SIGINT already raises `KeyboardInterrupt`. The previous handler is restored afterwards. The library root does not install signal handlers (a host owns its process); the kernel releasing `flock` on exit covers a host that is killed. This is the reason the mechanism is an OS lock and not a "create the file exclusively" lock, which a SIGKILL would strand.
- **Dry Run.** Taking the lock is Run machinery, not a Site write: a Dry Run takes it for real, so a Dry Run racing a real restore refuses rather than reporting a plan that cannot run. `SiteLock` therefore has no no-op implementation, which E002-S02-007's coverage test permits through the documented allowance.

### Error and edge case handling

- Second Run, same Site, different spelling (symlink, `/../`, trailing slash): refused — same canonical key.
- Second Run, different Site: proceeds.
- Holder killed with SIGKILL: next Run acquires immediately, logs `stale_lock_reclaimed` with the dead holder's Run ID; no manual removal.
- Holder receives SIGTERM: `finally` runs, lock released, workspace removed, exit `FAILED`; asserted by a subprocess test.
- Holder record corrupt or missing while the flock is held: refuse, naming the lock file path and saying the holder could not be identified.
- Site Root does not exist: `resolve(strict=True)` fails before any lock is taken → `InvalidSiteDescriptorError`, no lock file created.
- State directory not creatable or not writable: `SiteLockLocationError` naming the path → `NOT_READY`; the Run does not proceed unlocked.
- Re-entrant acquire by the same Run for the same Site: depth increments, outer release is the one that unlocks; an unbalanced release raises.
- PID reuse: irrelevant to correctness because ownership is the kernel lock, not the PID.

### Observability requirements

- `site_lock_acquired` (INFO) with `site_root` (canonical), `lock_path`; `site_lock_released` (DEBUG); `stale_lock_reclaimed` (WARNING) with the previous holder's `run_id`, `pid`, `started_at`; refusal logged as ERROR `site_locked` with the holder's fields, and the same fields in the stderr message.
- The holder record's `started_at` is UTC ISO-8601 with explicit offset (Consistency Conventions).

### Security considerations

- Lock directory `0700`, lock and holder files `0600`, so another user can neither read the holder's details nor hold or delete the lock.
- The holder record contains no credential and no Site content — only Run ID, PID, start time, hostname and the canonical path.
- The lock file name is a hash, so a Site Root path containing `/` or shell metacharacters never becomes a path component; the record is written with `json.dumps`, never string formatting.
- A lock directory resolving inside the Site Root is refused, closing the "restore deletes its own lock" hole AD-19 exists for.

### Testability approach

- `tests/adapters/test_site_lock.py` (unit-speed, real filesystem in `tmp_path`, lock directory injected): acquire/release; second acquire from a **separate process** (`multiprocessing` spawn) refuses with the holder's fields; canonical-key equivalence for symlinked and `..` spellings; re-entrant depth; unbalanced release; lock directory inside the Site Root refused; file modes.
- `tests/integration/test_site_lock_signals.py` (unmarked — needs no database; uses a backup with a database double and a hook that blocks): run the CLI in a subprocess, send SIGTERM, assert exit `FAILED` and the lock immediately acquirable; repeat with SIGKILL, assert the next acquire succeeds and logs `stale_lock_reclaimed`.
- `tests/unit/cli/test_lock_joining.py`: a nested entry point joining a Run Context for the same Site acquires nothing (recording `SiteLock`), and for a different Site acquires and releases its own.
- `tests/unit/cli/test_lock_order.py`: with a recording credential source and lock, the lock is acquired before `resolve()` is called, and released after the last phase, on success and on an exception.
- An end-to-end CLI case for `ExitCode.LOCKED` is the one E002-S02-006's enum-parametrised test requires for that member.

### Existing-library check

- Locking primitive: stdlib `fcntl.flock` — the OS's own advisory lock, released by the kernel on process death; preferred over `filelock` (py-filelock 3.x), which on POSIX wraps the same `flock` but exposes no holder metadata and adds a dependency for no capability gained here. The holder record is plain `json`.
- Per-user state directory: **`platformdirs`** (`user_state_path`), the maintained library for exactly this; resolving XDG and macOS conventions by hand is the domain the global rules forbid hand-rolling. This adds `platformdirs` as a runtime dependency (zero transitive dependencies, MIT); the implementer pins its current major after verifying the latest release, and adds it to `pyproject.toml` `dependencies`.
- Canonicalisation: `pathlib.Path.resolve(strict=True)`; hashing: `hashlib`; signals: stdlib `signal`.
- Decided 2026-10-20 (Shawn): `platformdirs` is accepted as a runtime dependency (the per-user state root shared by `locks/` here and Epic 3's `snapshots/` and Run Journal).
