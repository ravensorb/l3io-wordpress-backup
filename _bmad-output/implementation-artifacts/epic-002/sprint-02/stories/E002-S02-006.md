# E002-S02-006: Branch automation on what happened


**Implements:** FR-21


As an operator,
I want the exit code to tell me which kind of failure occurred,
So that my scheduler can retry a transient fault and alert on a real one.

**Acceptance Criteria:**

**Given** any run
**When** it ends
**Then** success exits 0 and every failure path exits non-zero
**And** the codes are the family table (database's `cli.Exit`: 0 OK, 1 FAILED, 2 USAGE, 3 REFUSED, 4 CREDENTIALS, 5 UNREACHABLE, 7 NOT_READY; 6 reserved) plus backup-only codes for verification failure and lock conflict, each documented
**And** the test covering every code derives its scope from the enum, never a hand-kept list
**And** invoking with no subcommand is an error, not a silent success
**And** no failure path returns a value the process then discards
**And** the code table lives in `domain/` as the source of truth, not scattered across the CLI

## Business acceptance criteria

### Outcome

A scheduler running `wpbackup2` can branch on the exit code alone: 0 means the Run succeeded; every failure exits non-zero with a code that names its kind, drawn from one documented table — the family codes shared with `l3io-wp-database` (0 OK, 1 FAILED, 2 USAGE, 3 REFUSED, 4 CREDENTIALS, 5 UNREACHABLE, 7 NOT_READY; 6 reserved for the family) plus two backup-only codes, verification failure and lock conflict. Running `wpbackup2` with no subcommand exits 2. The table is printed in `--help` epilog text and in the README, and both are checked against the enum in CI, so documentation cannot drift from behaviour.

### Non-goals

- Codes for failures that only later epics can produce (FR-7 non-empty-target refusal, AD-18 incomplete-journal refusal, FR-13 WP-CLI absence, FR-27 preflight). Those epics map onto this table (see Interface contracts); they do not edit it unless a genuinely new kind is needed, and then by appending.
- The `api/` exception contract (FR-23) — Epic 6. This story only maps package exceptions to codes at the CLI boundary.
- Changing `l3io-wp-database`'s `cli.Exit`.

## Technical acceptance criteria

### Interface contracts

- **`domain/exit_codes.py` — the source of truth (decision 3 of 2026-10-20; AG-26).** `class ExitCode(IntEnum)`: `OK = 0`, `FAILED = 1`, `USAGE = 2`, `REFUSED = 3`, `CREDENTIALS = 4`, `UNREACHABLE = 5`, `NOT_READY = 7`, `VERIFICATION_FAILED = 8`, `LOCKED = 9`. **6 is reserved for the family and is not a member**; `RESERVED: Final[frozenset[int]] = frozenset({6})`. Each member carries a one-line description in a `DESCRIPTIONS: Final[Mapping[ExitCode, str]]` table (no member without one). The module docstring states the table is append-only under §10: a value is never renumbered or reused.
  - Decided 2026-10-20 (Shawn): the two backup-only values are **8 = VERIFICATION_FAILED** and **9 = LOCKED** — the next free values after the family's 7, skipping the reserved 6. If the family later reserves a block above 7, these move before first release, never after.
- **Family conformance without an import.** `domain/` cannot import `l3io.wp.database` (an optional extra, and not pure). A contract test, run when the `database` extra is installed (it is in the dev group), asserts that for every member of `l3io.wp.database.cli.Exit`, `ExitCode[member.name] == member.value` — scope derived from database's enum, so a code database adds later that we lack fails here.
- **One mapping from failure to code, in `cli/`.** `cli/exit.py::exit_code_for(exc: BaseException) -> ExitCode` is the only translation: a `match` over the package's exception classes (E002-S01-001's `domain/errors.py` hierarchy) — `CredentialsError` → `CREDENTIALS`; `DatabaseUnreachableError` → `UNREACHABLE`; `VerificationFailedError`, `UnrecognisedArchiveError`, `UnsupportedFormatVersionError` → `VERIFICATION_FAILED`; `SiteLockedError` (E002-S02-008) → `LOCKED`; `MissingExtraError` and a preflight failure → `NOT_READY`; `RefusedError`-shaped refusals (`UnsupportedStorageSchemeError`, existing final Archive name, `RunContextActiveError`) → `REFUSED`; any other `BackupError` → `FAILED`; argparse errors → `USAGE`. A non-`BackupError` exception reaching `main` is a defect: it exits `FAILED`, is logged with `exc_info`, and a test asserts no code path in the package lets one escape for the documented failure modes. Each `BackupError` subclass may declare a class attribute `exit_code: ClassVar[ExitCode]` instead of a `match` arm; whichever is chosen, there is exactly one mechanism, not both.
- **Later epics map, they do not invent (AG-26).** Recorded in the module docstring: FR-7 and AD-18 refusals → `REFUSED`; FR-13 / FR-27 missing tools → `NOT_READY`; a decryption failure (Epic 4) → `CREDENTIALS` if a key is missing/wrong, `VERIFICATION_FAILED` if the ciphertext is corrupt. A new kind is added only by appending a member here, which E002 owns; another epic needing one raises it rather than editing `domain/`.
- **`cli/__init__.py::main(argv) -> int`** returns `int(ExitCode.X)` on every path; `run_from_cli` passes it to `SystemExit`. No subcommand → help on stderr, return `ExitCode.USAGE` (today's literal `2` becomes the enum). Every `run_*` function's return value reaches `SystemExit`; none is called for side effect with its return discarded.
- **Documentation generated, not hand-kept (AG-25).** The exit-code table and the CLI usage in the README are generated from `build_parser().format_help()` and `DESCRIPTIONS` by `tools/gen_cli_docs.py`, written between marker comments in `README.md`, and CI runs it in `--check` mode, failing on drift. The current README documents three flags that do not exist; this replaces that section. The parser's epilog lists the table from the same source.

**Added 2026-10-20 (gap pass; decisions 1, 2, 5, 6 and 7 of 2026-10-20).**

- **`domain/restore.py` (new, pure) — the restore vocabulary every epic consumes and none redefines (AD-5, AD-17, AD-25; E003-S01-001, E003-S01-002, E003-S02-003).**
  - `class RestoreMode(StrEnum)`: `FILES = "files"`, `FILES_CLEAN = "files-clean"`, `DATABASE = "database"`, `DATABASE_CLEAN = "database-clean"`, `ALL = "all"`, `ALL_CLEAN = "all-clean"` — FR-6's names verbatim. Four pure functions read FR-6's table through one `match` over every member ending in `assert_never`: `restores_files(mode)`, `restores_database(mode)`, `clears_site_root(mode)` (true for `files-clean`, `all-clean`) and `removes_database(mode)` (true for `database-clean`, `all-clean` only — decision 6: the database losing the cutover is dropped only in `*-clean` modes). No parameter annotated `RestoreMode` anywhere carries a default (`tools/check_mode_defaults.py`, AD-5).
  - `class RestorePhase(Enum)` in AD-17's order: `PREFLIGHT, VERIFY, SNAPSHOT, CLEAN, EXTRACT, REWRITE_CONFIG, LOAD_DUMP, SEARCH_REPLACE`, with `RESTORE_PHASE_ORDER: Final = tuple(RestorePhase)` and `is_subsequence(phases) -> bool`. The docstring carries AD-17's 2026-10-20 amendment verbatim in substance: `REWRITE_CONFIG` writes every key the plan changes **except** `DB_NAME`; the `DB_NAME` cutover to the loaded database is the **last journaled step of `LOAD_DUMP`**, after the load is checked; no `DB_NAME` write precedes the end of the load. Epic 3's phase-sequence test asserts that; this module states it.
  - `class Override(StrEnum)`: `NONEMPTY_FILES = "nonempty-files"`, `NONEMPTY_DATABASE = "nonempty-database"`; frozen `OverrideSet(waived: frozenset[Override])` with `waives(part: Literal["files", "database"]) -> bool` and `OverrideSet.none()`. `OverrideSet` is a distinct type from `RestoreMode` and has no field that can name a Mode or authorise a removal: an override only waives FR-7's non-empty-target refusal for one part (AD-25).
  - `class SnapshotPolicy(StrEnum)`: `TAKE = "take"`, `SKIP = "skip"` — closed; no consumer declares a default for it (E003-S02-003). `tools/check_mode_defaults.py`'s guarded set gains `SnapshotPolicy` and `OverrideSet`, confirmed by planting a defaulted parameter of each in the tool's planted-violation test.
- **The AD-25 table, decided (2026-10-20; settles the table questions E003-S01-001 and E003-S01-002 left open).** The restore subparser's mode-selecting flags are `--mode {files,db,all}` (frozen), `--cleanfirst` (frozen), `--force` (frozen) and one new flag, **`--drop-database`** (`store_true`; AD-22 permits additions). Their meanings, which the table encodes and nothing else re-derives:
  - `--mode` chooses the parts restored (`db` → database, through E002-S01-002's one CLI→domain mapping; restore reuses `CLI_MODE_TO_SCOPE`, no second spelling table).
  - `--cleanfirst` authorises **clearing the Site Root** and nothing else. `--drop-database` authorises **removing the database that loses the cutover** and nothing else. They are the two separate destruction authorisations FR-6 requires, so `all-clean` is reachable only by giving both, and no single flag authorises all destruction (§7.1).
  - `--force` yields `OverrideSet` waiving FR-7's non-empty-target refusal **for exactly the parts the resolved Mode restores** (`NONEMPTY_FILES` iff `restores_files`, `NONEMPTY_DATABASE` iff `restores_database`). It selects no Mode and authorises no removal. `--cleanfirst` without `--force` against a non-empty Site Root therefore refuses (AD-25, read plainly).
  - Rows (`force` doubles each row, adding the waivers above): `files` → `FILES`; `files --cleanfirst` → `FILES_CLEAN`; `db` → `DATABASE`; `db --drop-database` → `DATABASE_CLEAN`; `all` → `ALL`; `all --cleanfirst --drop-database` → `ALL_CLEAN`. Every other combination — `files --drop-database`, `db --cleanfirst`, `all --cleanfirst` alone, `all --drop-database` alone, and any with both on `files`/`db` — maps to a `FlagRejection(reason: str, use_instead: str)` naming the flag combination that would express a real Mode (e.g. `db --cleanfirst` → "`--cleanfirst` clears the Site Root, which `--mode db` does not restore; to remove the previous database use `--drop-database`"). A rejection is a table entry, not a default branch, and exits `USAGE`.
  - `domain/flag_map.py`: `COVERED_FLAGS = frozenset({"mode", "cleanfirst", "drop_database", "force"})`; `FLAG_MAP: Final[Mapping[FlagCombination, tuple[RestoreMode, OverrideSet] | FlagRejection]]` written out as a **literal** of all 24 entries (3 × 2 × 2 × 2) — not generated by a comprehension, so each row is reviewable against FR-6; `resolve_flags(combination: FlagCombination) -> tuple[RestoreMode, OverrideSet]` indexes it with no `.get` default and raises `FlagCombinationRejectedError(UsageError)` for a rejection; `authorizing_combination(mode: RestoreMode, part: Literal["files", "database"]) -> FlagCombination` is the inverse lookup E003-S01-002 uses to name the waiving flag in its refusal message (derived from the table, never typed into a message).
  - Behaviour change from v0.2.21, named in the release notes: `--force` no longer maps to `ALLCLEAN` (B-3); `--cleanfirst` no longer removes the database; `--mode db --cleanfirst` is now a usage error naming `--drop-database`.
- **Which restore flags are mode-selecting is declared at the flag, not in a list (AD-25 enforcement, global rule 4).** The restore subparser puts its mode-selecting flags in an argument group titled `restore mode` and every other `store_true`/`choices` action in `restore options`. `tests/contracts/test_flag_map.py`'s derivation is narrowed to the `restore mode` group's actions, and a new assertion fails if any `store_true`/`choices` action on the restore subparser belongs to neither group — so a new flag must be classified where it is defined. Planted-violation cases: a `store_true` added to `restore mode` without a table entry fails; one added outside both groups fails. The table's docstring states that `--no-safety-snapshot`, `--snapshot-dir`, `--resolve-interrupted-run` and the encryption flags are `restore options` and do not affect `(RestoreMode, OverrideSet)` (E003-S02-003's request).
- **New flags (AD-22 permits additions; each registered here with its help text, documented by `tools/gen_cli_docs.py`).**
  - Restore: `--no-safety-snapshot` (`store_true`, `restore options`) → `SnapshotPolicy.SKIP`, else `TAKE` (AD-26 as decided 2026-10-20: the explicit opt-out); `--snapshot-dir PATH` (value; default per E003-S02-003's per-user state location); `--resolve-interrupted-run RUN_ID` (value; requires the interrupted Run's ID, so no blanket flag can resolve a journal nobody read — E003-S02-005); `--drop-database` (above).
  - Encryption: repeatable `--recipient AGE_RECIPIENT` (`action="append"`), `--recipients-file PATH` on backup and restore (restore uses them for the Safety Snapshot); repeatable `--identity-file PATH` on restore and verify (decryption); and `--encrypt-with-passphrase` (`store_true` — requests passphrase encryption; the secret itself is obtained only through E002-S02-004's `resolve_passphrase` chain, **never as an argument value**: no flag takes a passphrase, asserted by a test that every action whose `dest` contains `passphrase` is a `store_true`).
  - Backup: repeatable `--exclude PATTERN`, `--no-default-excludes` (`store_true`), `--list-default-excludes` (`store_true`; prints the default set and exits `OK` without a Run).
  - Until the epic that implements a flag's behaviour has landed (encryption — Epic 4 story 4.3; exclusions — Epic 4 story 4.1; restore — the proposed restore composition-root story), the flag is **accepted-and-explained**: the Run exits `USAGE` naming the missing feature, exactly as the restore flags already are, and never silently ignores it. Which implementation is bound is decided only in the composition roots.
- **The exit-code mechanism, decided (2026-10-20; E004-S01-003 item 6).** Of the two mechanisms above, **the class attribute** is chosen: `BackupError.exit_code: ClassVar[ExitCode] = ExitCode.FAILED`, overridden on the classes that map elsewhere (`CredentialsError` → `CREDENTIALS`, `DatabaseUnreachableError` → `UNREACHABLE`, `VerificationFailedError`/`UnrecognisedArchiveError`/`UnsupportedFormatVersionError` → `VERIFICATION_FAILED`, `SiteLockedError` → `LOCKED`, `MissingExtraError`/`PreflightFailedError` → `NOT_READY`, `RefusedError` → `REFUSED`), and a new `UsageError(BackupError)` → `USAGE` in `domain/errors.py`. `exit_code_for` returns `type(exc).exit_code` for a `BackupError`, `USAGE` for an argparse error, `FAILED` (logged with `exc_info`) otherwise — no `match` over classes. A later epic's class inherits its code from the E002 base it subclasses, or declares `exit_code` itself with an **existing** member, so `adapters/crypto`'s `EncryptedMemberCorruptError` declares `exit_code = ExitCode.VERIFICATION_FAILED` and its `EncryptionConfigError` subclasses `UsageError` — neither needs an edit in `cli/`. Adding an `ExitCode` member stays E002's alone.

### Error and edge case handling

- No subcommand: exit 2, help on stderr.
- Unknown subcommand or flag, bad `--mode` value: argparse exits 2 itself; asserted to equal `ExitCode.USAGE` (not assumed).
- `--only-appointed-in-asg` (accepted-and-explained, AD-22): exits `USAGE` with a message naming the removal of `chesney` — the flag itself is added by the CLI-surface work below.
- An exception raised while logging the failure (e.g. broken stderr): the original code is still returned.
- `KeyboardInterrupt`: exit 130 (shell convention) is **not** in the enum and not claimed; the CLI lets Python's default handling apply after the Run's `finally` blocks run. Stated so nobody adds a silent catch.
- A failure path that returns a value instead of raising: forbidden — `run_*` functions either return `ExitCode.OK` or raise; a test drives each documented failure and asserts a non-zero exit.

- *(Added 2026-10-20.)* A rejected flag combination (e.g. `restore --mode db --cleanfirst`): exit `USAGE`, nothing read beyond argument parsing, message from the table entry naming the flag that would express a real Mode.
- `--list-default-excludes` combined with any Run-requiring argument: it prints and exits `OK` without opening a Run or reading the Site Root.
- A flag whose feature has not landed: exit `USAGE` naming the feature and the story that delivers it; a test per such flag, derived from the parser's actions in the `accepted-and-explained` set the composition root declares, so the set cannot outlive the feature (the test fails once the feature is bound and the flag is still declared unimplemented).

### Testability approach

- `tests/unit/domain/test_exit_codes.py`: every `ExitCode` member has a `DESCRIPTIONS` entry; no member's value is in `RESERVED`; values are unique (`@unique`). Parametrised from `list(ExitCode)` — **scope from the enum, never a hand list** (the epic AC).
- `tests/contracts/test_exit_codes_family.py`: the database-`Exit` conformance check above, with a scope assertion that database's enum is non-empty.
- `tests/unit/cli/test_exit_mapping.py`: every concrete `BackupError` subclass (found by walking `BackupError.__subclasses__()` recursively after importing every package module) maps to a code, and the mapped code is not `OK`; one end-to-end CLI case per `ExitCode` member except `OK`, parametrised from the enum, each driving a real failure through `main` with doubles — a member with no reachable case fails the test (so an enumerated code nothing can produce is caught, the FR-23 "reachable raise site" shape).
- `tests/contracts/test_cli_docs.py`: runs `tools/gen_cli_docs.py --check`; CI also runs it as a step beside `AD-25 flag map is total` in the `contracts` job.
- **Frozen CLI surface conformance (AG-10)**, owned here because this story owns the CLI's outward contract tests: `tests/contracts/test_cli_surface.py` asserts the parser accepts all nineteen v0.2.21 spellings (`--version`, `--log-level`, `--whatIf`, `--wp-dir`, `--mode`, `--archive`, `--cleanfirst`, `--admin-username`, `--admin-password`, `--admin-credentials-aws-secret-id`, `--admin-credentials-aws-region`, `--only-appointed-in-asg`, `--new-site-url`, `--new-site-home-url`, `--new-db-host`, `--new-db-name`, `--new-db-user`, `--new-db-password`, `--force`) on the subcommands they lived on, `backup` and `restore` exist, `python -m wpbackup2` and the `wpbackup2` console script both reach `main` (subprocess check against the installed environment), and `--only-appointed-in-asg` fails with the explanation rather than argparse's "unrecognized arguments". The expected list is taken **from the legacy parser** (`wpbackup2/__main__.py`, kept on disk) by AST, not typed into the test, so the reference cannot drift; the test fails if that file is deleted without replacing the reference with a committed snapshot. Restore-only flags are registered on the restore subparser by this story as accepted-but-not-yet-implemented (exit `USAGE` naming the missing feature) so the surface is frozen before Epics 3/5/7 fill it — and every flag added to the restore parser gets its AD-25 `flag_map` entry in the same change, as `tests/contracts/test_flag_map.py` enforces.
  - Decided 2026-10-20 (Shawn): the AD-25 `(RestoreMode, OverrideSet)` table stays in this story. Registering the restore flags here makes `--cleanfirst`, `--force` and restore's `--mode` AD-25 dimensions now, so `domain/restore.py` and the table in `domain/flag_map.py` land with them (see the 2026-10-20 additions below); no other epic edits `domain/`.
- `python -m wpbackup2` requires a `wpbackup2` importable module; the legacy `wpbackup2/` tree occupies that name on disk but is excluded from the wheel. Providing the module invocation is part of this test's scope and of the CLI surface work; Decided 2026-10-20 (Shawn): the `python -m wpbackup2` case stays `xfail(strict=True, reason=...)` naming AD-22's open legacy-tree item, so it turns into a failure the moment the module invocation starts working without the marker being removed — never silently skipped.

- *(Added 2026-10-20.)* `tests/unit/domain/test_restore_vocabulary.py`: FR-6's four columns per `RestoreMode`, parametrised from the enum, checked against a table transcribed from the PRD in the test's docstring; `RestorePhase` order equals AD-17's; `is_subsequence` rejects a reordering.
- `tests/contracts/test_flag_map.py` (extended as above) plus `tests/unit/domain/test_flag_table.py`: every `RestoreMode` member is reached by exactly one `force=False` combination (FR-6's round-trip, scope from the enum — an unreachable Mode fails); `ALL_CLEAN` is reached only by combinations containing both `cleanfirst=True` and `drop_database=True`; no single flag's `True` value turns a non-clean Mode into one where both `clears_site_root` and `removes_database` hold; `force` never changes the Mode of a row (pairs of rows differing only in `force` have equal Modes); every `FlagRejection` names a flag.
