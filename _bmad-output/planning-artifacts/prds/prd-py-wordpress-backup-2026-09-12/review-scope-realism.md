# Verdict

**Not survivable as scoped.** The v1.0 cut in §13.2 removes four feature-shaped items (encryption, remote storage, retention, scheduling) but keeps the two most expensive *structural* commitments — a versioned, deprecation-policed Python API contract (FR-22–24, §10) and a permanent archive-format compatibility guarantee (§8) — sitting on top of what is, in effect, a full rewrite of a currently non-functional 909 LOC codebase. The document diagnoses its own over-scoping correctly (SM-C2, the risk register, FR-18's note) and then acts on that diagnosis only for the one item that was already obviously separable (scheduling). That is a specific, real failure, not a rhetorical one.

---

## 1. Is the v1.0 cut in §13.2 a real MVP?

No. Count it: 27 FRs total. §13.2 defers only FR-4 (encryption), FR-16 (remote storage), FR-17 (retention), FR-18 (scheduling), and the AWS Secrets Manager half of FR-14. That leaves **23 of 27 FRs, plus every NFR in §6, plus both §8 contracts and all of §10's deprecation machinery, inside v1.0.** This is not an MVP cut; it is "ship everything except the parts that need a network call to a remote service."

Cost relative to the existing 909 LOC (source only; 1,265 LOC including tests — confirmed by direct count, `wpbackup2/**/*.py`):

- The existing code is not a base to extend; per the addendum's own carried-forward findings (§D), it is broken in ways that require rewriting, not patching: `restore_mode` is discarded (B-3), `--cleanfirst`/`--mode` are inert (M-17), database-only backup produces no archive (M-3), failure paths exit 0 (M-16), credentials leak into `argv` and logs (B-4), `extractall` has no containment (M-14), there is no manifest, no structured logging, no CI, and the tests are "broken and assertion-free" (M-9/10/11).
- On top of that near-total rewrite, v1.0 asks for capabilities that don't exist in the codebase **at all** today: a Manifest/Archive-format with a version gate (FR-3, FR-10), a Safety Snapshot mechanism (FR-8), serialization-safe URL rewriting via WP-CLI delegation (FR-12 — the addendum states plainly that today's code "never touches `wp_options` or postmeta," i.e., this is 100% new, and is called out as "the single largest functional gap against every credible competitor"), a pluggable Credential Provider abstraction (FR-14), a fully typed public Python API with an exception contract (FR-22–24), structured logging correlated by Run ID across subprocess boundaries (FR-20), Dry Run threaded through every destructive operation (FR-19), and a packaging/CI/dependency-staleness overhaul (FR-25–27) that additionally requires coordinated changes in **two sibling repositories** (`wpconfigr` needs publishing and a naming decision — Q-6; `wpdatabase2` needs `boto3` demoted to an optional extra — Q-9, explicitly flagged as unsatisfiable "from this repository alone").
- Rough order of magnitude: this is plausibly 4–6x the current codebase in new/rewritten production code, before counting the test fixtures NFR-8 asks for (mocking `mysqldump`/`mysql`/`wp` well enough to test most behavior without a live WordPress or MySQL is itself a nontrivial harness), documentation (the §11 runbook, exception reference, public-surface docs), and cross-repo coordination work that isn't even fully this maintainer's call to make alone. For a solo maintainer this is many months of elapsed calendar time — during which the actual "why now" problem (package does not install) sits unresolved, because it's bundled behind the whole v1.0 build rather than shipped as its own release.

**FRs that should move out of v1.0, specifically:**

- **FR-22, FR-23, FR-24** (typed API, exception contract, declared public surface) — this locks a second semver'd, deprecation-policed contract before the underlying domain model (Site Descriptor, Restore Mode, Credential Provider) has survived a single release cycle of real usage. Ship these as an *internal* module used by the CLI in v1.0; promote to a supported, versioned API in v1.1+ once the shape has proven itself. This is the single highest-leverage cut available and the PRD does not take it.
- **FR-9's auto-create-database-and-user behavior** ("ensures the target database and user exist before loading the Dump") — this is provisioning, not restore, and it adds a MySQL-user-creation security surface that a v1.0 focused on "it installs, and it cannot hurt you" doesn't need. Require the DB/user to pre-exist in v1.0; add auto-provisioning later if operators ask for it.
- **FR-14's provider *extension point* as a locked contract** ("a library caller can implement and pass a provider without subclassing internal types") — fine as an internal seam in v1.0, premature as a documented, stable extension contract before FR-22's API contract itself is deferred.
- The **cross-repo packaging work implied by FR-25/26** should be explicitly split: publishing `wpconfigr` and cutting `chesney` are cheap and should ship immediately as their own release (the addendum already says as much in §C.3 — "should land first"), decoupled from the rest of v1.0's build-out.

## 2. Capabilities that will rot

Remote storage (FR-16) and scheduling (FR-18) are the obvious ones and the PRD names both. Others it doesn't flag with the same clarity:

- **FR-4, encryption at rest.** Deferred to v1.1, but once shipped it is a *permanent* liability of a different character than a feature: any future change to cipher, KDF parameters, or the encryption library creates a backward-decryptability obligation, and getting it wrong is a security defect, not a bug. §8 states the Archive format's compatibility guarantee is "stronger than the API's" — encryption parameters live inside that same forever-readable Manifest. This is quietly one of the largest long-run maintenance commitments in the whole document and it is discussed only as a feature-timing question (the FR-4 note), never as a maintenance-forever question.
- **FR-14's AWS Secrets Manager provider.** Blocked today by `wpdatabase2`'s hard `boto3` dependency (Q-9), which the PRD admits it cannot resolve from this repository alone. If the sibling package doesn't change, this provider either ships as documented-but-broken or becomes exactly the kind of transitively-mandatory dependency the PRD's own "Why Now" section identifies as the root cause of the current outage. This is a capability whose maintenance already depends on a repo this PRD explicitly declines to govern (§9's Q-10: "no owning document").
- **FR-26's mechanical staleness check** ("fails the build when a declared runtime dependency... has had no release within a documented staleness window") is itself infrastructure that needs a data source, a threshold policy, and periodic review of false positives — a checker that itself can go stale or get disabled under time pressure the first time it blocks an urgent release.
- **FR-17, retention/pruning**, multiplies with every Storage Target added — each new target needs its own tested prune/list/verify path. It rots by combinatorial neglect, not by external API drift.
- **The FR-22–24 typed API + §10 deprecation policy**, taken together, is the deepest rot risk of all: it doesn't fail loudly like a broken S3 client, it fails by the maintainer quietly abandoning the deprecation discipline under time pressure — a breaking change ships in a "minor" release, the changelog stops mentioning deprecations, and the "supported contract" framing becomes aspirational. That failure mode is invisible until a downstream consumer's pin breaks.

**What should be delegated instead of owned:** remote storage should lean on an existing multi-backend tool (e.g., `rclone`, which already speaks S3, SFTP, and dozens of others) rather than wpbackup2 hand-maintaining `boto3` + an SFTP client + rsync subprocess plumbing as three separate first-class integrations — this is the same "don't hand-roll what a maintained library does" logic the PRD already applies correctly to WP-CLI delegation (FR-12), just not applied to FR-16. The AWS Secrets Manager provider could similarly be deferred indefinitely in favor of the generic environment/file-based Credential Provider, which already covers "a secret manager that exports to the environment" without wpbackup2 owning an AWS-specific integration at all.

## 3. The three-supported-contracts problem (§8, §10)

Declaring the CLI, the Python API, *and* the Archive format as versioned contracts with semver and deprecation cycles (§10: "Semantic versioning across all three contracts") triples the process cost of any change that touches more than one surface — and many will, since a Restore Mode rename, say, touches the CLI flag, the API parameter, and potentially Manifest metadata simultaneously. Each contract change requires: implement the new form, keep the old form functioning, emit a deprecation warning naming the replacement, log it in the changelog, and track it for removal — for a single maintainer, done three times over for a single semantic change.

Realistic failure mode: not that all three contracts break loudly, but that the deprecation discipline erodes quietly and unevenly. The archive-format contract is the one that matters most (§8 says so directly — "This matters more than the other two: operators hold Archives for months") and it is also the one hardest to test faithfully, since faithful testing means keeping old-format fixtures around and continuing to exercise them release after release — exactly the kind of untested-by-neglect legacy path that produces silent regressions (the CLAUDE.md example of a hand-rolled YAML parser breaking on U+0085 is the same shape of failure: a compatibility path nobody was actively exercising). The more probable outcome for a solo maintainer under time pressure is either (a) a breaking format or API change ships in a minor release, quietly violating §10, or (b) the maintainer becomes reluctant to change *anything* in the shared surface because the deprecation tax is too high, and quality stagnates instead of degrading loudly. Neither is named in the PRD's risk register, which discusses dependency and archive-corruption risk but not maintainer-process risk from the versioning policy itself.

A one-maintainer project can sustain one strictly-versioned contract. It should pick the one that's actually load-bearing for trust — the Archive format, since that's what protects users' existing backups — and treat the CLI and the pre-1.0 Python API as best-effort/flexible until usage has proven their shape, formalizing deprecation policy on those only once real consumers exist to break.

## 4. Where the PRD already knows — diagnosis without treatment

The PRD is self-aware about over-scoping at exactly the level of abstraction that costs nothing to concede, and stops short of applying that awareness where it would cost something:

- **SM-C2** states plainly: "Growth in capabilities is not a success signal for a small OSS project; it is a maintenance liability... the deferrals are not a backlog to burn down on principle." This logic applies just as much to FR-22–24 (a whole second contract) and to the cross-repo packaging obligations in FR-25/26 as it does to the four items actually deferred — but it is only invoked to justify not un-deferring FR-4/16/17/18 later, never to question whether more should have been deferred in the first place.
- The **risk register** (§12) names the exact risk this review was asked to test — "Scope selected here exceeds sustainable maintenance for a small OSS project" — with mitigation "Phased MVP (§13); WP-CLI delegation over ownership; scheduling flagged for cut (FR-18)." The mitigation is narrower than the risk: two of its three named mechanisms (the phased MVP, the scheduling cut) touch one FR, and the third (WP-CLI delegation) addresses a different risk (relocation-corruption) entirely. Nothing in the mitigation touches the API-contract sustainability problem, the three-contract versioning problem (§8/§10), or the cross-repo coordination problem the PRD names in the very next section (§9's Q-10: "the cross-package compatibility and release-coordination story has no owning document... the risk is that it stays unowned by default").
- **FR-18's [NOTE FOR PM]** is the one instance where the document's self-awareness produced action: it recommends cutting scheduling, and §13.2 does defer it. Credit for that — it is real evidence the mechanism can work.
- The pattern across all three: the document correctly names the disease (SM-C2, the risk row) and administers the treatment only to the one symptom that was already cleanly separable and non-architectural (scheduling wraps `cron`/`systemd` either way — cutting it costs nothing structurally). The two commitments that are hardest to walk back later precisely because they are architectural rather than additive — a versioned public API contract, and a permanent archive-format compatibility guarantee — are the ones left untouched by a self-diagnosis that, on its own stated terms, should have reached them first. **This is the specific failure the prompt asked to name plainly, and it is what is happening**: self-aware over-scoping, not blind over-scoping — arguably worse, since the tools to fix it are already in the document and go unused.

One more, smaller instance of the same "records but doesn't enforce" pattern: §0 states FRs are "numbered globally (FR-1…FR-31)," but the document's actual FRs stop at FR-27. Minor, but it's the same shape of defect the user's own engineering rules call out — a stated coverage claim that a reader would have to check by hand to discover is false.

## 5. The counterfactual: what a genuinely minimal v1.0 looks like

Split what is currently one v1.0 into two releases. **Release A** (weeks, not months): resolvability only — publish `wpconfigr`, cut `chesney`, add a lockfile and CI. This alone fixes the entire "Why Now" problem (§2) and ships no new product behavior. **Release B**, the actual v1.0 product bet: a CLI-only tool doing full-site backup and restore to a **local** Storage Target, with real Restore Mode semantics that fix the current defects (honored `restore_mode`, no unconditional `rmtree`, DB restore that fails loudly instead of silently skipping), a Safety Snapshot before any destructive restore, and Relocation via WP-CLI delegation — because that's the one capability that actually differentiates this from `mysqldump | tar`, and the PRD's own Vision section already concedes that hand-rolled script pattern already handles encryption and remote storage adequately via existing tools (restic/rclone) that operators can compose around this CLI. The Python API stays internal and unversioned; the archive format carries a version field but not yet a forever-compatibility promise; encryption, remote targets, retention, scheduling, and AWS all wait for real signal that operators want them from *this* tool rather than from the restic/rclone layer already sitting next to it.

**Is the PRD's v1.0 already this? No.** It is substantially larger, specifically because it keeps both of the expensive structural commitments (the typed API contract and the permanent archive-format guarantee) that the counterfactual defers, while trimming only the additive feature list. The gap between the PRD's v1.0 and this counterfactual is not a feature count — it's exactly the two contracts identified in §3 above.
