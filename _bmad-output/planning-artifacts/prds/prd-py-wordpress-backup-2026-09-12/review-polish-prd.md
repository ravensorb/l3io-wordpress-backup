# Editorial review — `prd.md`

**Lenses run:** `structure`, `prose` (editorial only). Scope, strategy and factual accuracy were
reviewed elsewhere and are explicitly out of scope here; content is treated as sacrosanct and only
its organization and expression are critiqued.

**Purpose/audience read:** This document exists to help the maintainer, contributors, and the
downstream BMad workflows (UX, architecture, epics and stories) build wpbackup2 from a stable,
citable set of numbered requirements.

**Structure model applied:** Strategic/Context (Pyramid) — top-down, MECE groups, most critical
information first, evidence supporting arguments rather than leading them. The document fits this
model well; the findings below are mostly local damage from the recent in-place rewrite, not a
shape problem.

**Reader type:** humans. **Style guide:** Microsoft Writing Style Guide.

**Word metrics:** 10,241 words total, 60 headed sections. Largest sections: §15 Open Questions
(562), §3.3 Key User Journeys (483), §14 Success Metrics (435), §4 Glossary (402), §9 Runtime
Targets (374), §6 NFRs (364), §1 Vision (364).

**Mechanical baseline:** `check_prd.py` passes — 29 FRs defined, FR-1…FR-29 contiguous, 11 Qs
listed, 1 open `[ASSUMPTION]` tag, every FR placed in a release phase. Every `§N` pointer in the
document resolves to an existing heading. The findings below are the things that check cannot see.

## Summary

- **Total recommendations:** 24 rows (18 structure, 6 prose), plus 7 minor fixes rolled up.
- **Estimated reduction if all accepted:** ~700 words cut, ~50 added — a net **~650 words, 6.3%**
  of 10,241. §15 alone accounts for more than half of it.
- **Length target:** none was provided, so no target assessment is made.
- **Comprehension trade-offs:** the §15 and §16 condensations trade a browsable narrative for a
  table. For this reader set — a maintainer and downstream generation workflows — the table is
  the better shape, but it does remove the reasoning-in-prose that makes those sections readable
  end to end. If either section is valued as a standing record of *why* rather than *what*, keep
  the prose and accept the redundancy; say so explicitly in the section opener so the next editor
  does not re-cut it.
- **Deliberately preserved:** §13.2's "v1.0 is a **rewrite, not an increment**" warning (it is
  load-bearing for estimation and looks like meta-commentary but is not); the X-not-Y antithesis
  throughout (established voice); the `[NOTE FOR PM]` callouts (they provide whitespace and flag
  live decisions); §4 Glossary's overlap with the FR bodies (definition-then-use is reinforcement,
  not duplication).

## Mechanical follow-up

Three of the findings above are invisible to `check_prd.py` **because of its scope, not its
rules** — it derives the FR set from the document but stops at FRs. Two cheap extensions would
close the classes found here:

1. **Series contiguity for every `ID-<n>` series, derived from the document.** Collect the prefix
   set from the text (`FR`, `SM`, `UJ`, `NFR`, `Q`) rather than hard-coding it, then apply the
   existing gap check to each. Plant `SM-7` with `SM-5`/`SM-6` absent to prove the guard sees a
   series it was not written for. This catches the SM-5 gap.
2. **Section-pointer content check.** For each `§N` reference, assert the target heading exists —
   the document currently passes this — and additionally flag a pointer whose target contains none
   of the reference sentence's distinctive nouns. That is a heuristic, not a proof, so state that
   limit next to the check: it would have caught "multisite … see §12", but it will not catch
   every stale pointer, and nothing should claim it does.

Both are scope extensions of a guard that is already correct. Neither requires a hand-kept list.
